## 现在就开始

今天只做三件事，不要先通读和扩充整个计划：

1. 在[能力改善计分板](../../tracking/03-能力改善计分板.md)填写计划起止日期；
2. 完成本页“第 0 周”的六项基线任务并保存录音/答题结果；
3. 根据最低分选择第 1 周唯一的行为重点，同时按既定内容开始个人作品 A0 和第一组算法题。

## 一、90 天以后希望看到的变化

| 维度 | 过去容易出现的模式 | 90 天目标 | 验收证据 |
|---|---|---|---|
| 业务理解 | 接到任务后再局部查背景 | 先建立用户、流程、指标、数据和上下游全景 | 三个项目各有业务流程和指标树；能在 3 分钟讲清 |
| 结果意识 | 模型/代码完成即接近 Done | 项目开始就定义模型、系统、采用、业务和护栏指标 | 每个项目有指标树、观测方式和回看日期 |
| 沟通表达 | 按思考或排查过程讲 | 结论先行，围绕听众要做的决策组织信息 | 每周录音；90 秒进度汇报；3 分钟项目表达 |
| 主动汇报 | 等别人询问状态 | 固定节奏同步结果、风险、请求和 ETA | 每周至少一份状态更新；风险不静默跨周 |
| Ownership | 主要对实现负责 | 同时管理目标、范围、依赖、风险、效果和收尾 | 个人 Agent 作品完整走过立项、周报、Demo、评测和复盘 |
| 工程与 AI 验证 | 新环境适应较慢，验证依赖临场 | 代码能解释、能测试、能排障，AI 只加速不替代判断 | 代码审查清单、失败用例、调试记录和复盘 |
| 面试编码 | 知识存在但手感不足 | Python 中等题限时完成并主动测试 | 前六周至少 48 道算法新题 + 2 道工程题、至少 24 次间隔复做、3 次模拟中通过 2 次 |
| Agent Workflow | 概念较多，公开实现证据不足 | 完成一个可运行、可恢复、可评测的个人作品 | 代码、README、架构图、Golden Set、Eval 和已知限制 |

所有“当前水平”先写未测，不能凭感觉给高分。第 0 周测完后再填入[能力改善计分板](../../tracking/03-能力改善计分板.md)。

## 二、第 0 周：建立真实基线

只用半天，不提前补课：

1. 录一段 2 分钟自我介绍；
2. 录一段 10 分钟时效或阈值项目讲述；
3. 用 90 秒口头汇报一个模拟项目的进度和风险；
4. 限时 30 分钟做一道中等算法题；
5. 用 30 分钟设计一个带工具和人工审批的 Agent Workflow；
6. 给业务、表达、项目、Agent、编码五项各打 0–10 分，并写下证据。

90 天后使用同类题目复测。否则很容易出现“看了很多，所以感觉提高了”的错觉。

## 三、0–30 天：先建立基本工作系统

### 第 1 周：业务问题和项目叙事

三项关键交付：

1. 选择时效或阈值作为主项目，完成一页业务 Brief、指标树和 3 分钟讲法；其余两个项目后续逐周补，不在第一周全部铺开；
2. Agent 作品完成 A0：确定性 Workflow、状态 Schema 和 10 个用例；
3. LeetCode 完成数组、HashMap、双指针、滑动窗口 10 题。

验收：不讲 SQL 编写过程和普通代码细节，也能在 3 分钟内解释项目为什么值得做。有余力时再做 45 分钟深挖，不列为本周必做。

### 第 2 周：沟通、汇报和工具契约

三项关键交付：

1. 使用统一模板完成 3 次三分钟录音、一份 Agent 周状态和一次模拟风险同步；最后一次录音作为行为面验收；
2. Agent 作品完成 A1：Tool Schema、最大步数、超时、错误分类和写入确认；
3. LeetCode 完成链表、栈、队列和堆 8 题。

验收：任何进度都能按统一的[项目管理与汇报模板](../../templates/项目管理与汇报模板.md)在 90 秒内讲清。

### 第 3 周：Ownership 和主动推进

三项关键交付：

1. 为个人 Agent 写一页立项卡和风险/决策日志；同时为第二个滴滴项目补业务指标树；
2. Agent 作品完成 A2：小型 RAG 或证据检索、Context 装配和来源引用，并用一次系统设计模拟验收；
3. LeetCode 完成树、二分、DFS/BFS 和 Top-K 10 题。

验收：能够回答为什么做、谁依赖谁、什么算完成、何时升级风险，而不只回答怎样实现。

### 第 4 周：结果闭环和第一次月度复盘

三项关键交付：

1. Agent 作品完成 A3 第一版：先建立 20 条 Golden Set，覆盖正常、缺信息、硬条件不满足、证据冲突和应拒答；
2. 整理 4 个证据最强的真实行为故事并完成一次综合模拟，不足处标记待补，禁止编造；
3. LeetCode 完成图、拓扑、回溯和基础 DP 8 题，并用同类录音/答题完成第 30 天复测。

验收：每个技术决策至少对应一个指标，每个故事都能说出自己的动作、结果和反思。

## 四、31–60 天：形成可展示的技术与行为证据

### 第 5 周：工程可靠性

三项关键交付：

1. Agent 作品完成 A4：状态持久化、失败恢复、最小权限、安全降级和工程化；
2. 选择一个真实故障场景，完成 Python/后端可靠性复习、复现、测试和一次 90 分钟全真模拟；
3. LeetCode 完成 DP 与混合题 8 题，再做 LRU、限流器等工程题 2 题。

验收：编码结束后能主动给复杂度、边界测试和失败处理；Agent 能从至少两类失败恢复或安全终止。

### 第 6 周：把能力转化成面试输出

三项关键交付：

1. 完成个人 Agent 作品第一版发布包：README、架构图、至少 30 条评测及一份包含已知限制的 Eval 报告；扩展到 50 条作为后续可选项；
2. 选择 1 个 A 档 JD 做定向准备，并完成 1 次全真模拟；其余 JD 和第二次模拟移到第 7 周；
3. LeetCode 新题 4 题并复做最关键的 4 道错题；完整第 0 周同类复测移到第 7 周。

验收：项目、知识、编码、表达均达到 7/10，且没有单项低于 6；所有项目表述符合事实台账。

### 第 7–8 周：进入真实面试循环

三项关键交付：

1. 每周筛选 5 个 JD；面试前只补前三个缺口，面试后 24 小时内完成复盘；
2. 第 7 周先完成第 0 周同类复测和第二次全真模拟；之后编码以限时混合题和错题复做为主，每周只安排一次最需要的行为面或技术模拟；
3. Agent 项目只修影响 Demo、Eval 或可靠性的缺口，不再扩展新功能。

验收：同类问题第二次不因相同原因失分；项目数字不混乱；能清楚区分做过、验证过和设计过。

## 五、61–90 天：稳定迭代，不再靠冲刺

这一阶段根据真实面试数据动态调权：

- 项目讲述低于 7 分：暂停新知识，连续做三次项目深挖；
- 编码连续两次失败：每天前 45–60 分钟固定编码；
- Agent 概念会背但设计不完整：只做白板题和作品修复；
- 后端频繁失分：将 MySQL、Redis、MQ、并发和排障提高到 25%；
- 没有面试反馈：重新检查岗位定位、简历证据和投递渠道，不用继续堆课程逃避投递；
- 已有高频面试：停止追新框架，围绕真实题目复盘和二刷。

第 90 天做一次完整验收：

1. 2 分钟自我介绍；
2. 两个项目各 15 分钟深挖；
3. 30 分钟 Agent 系统设计；
4. 30 分钟 Python 中等题；
5. 20 分钟行为面；
6. 复核个人 Agent 作品及 Eval；
7. 输出下一季度只保留的三个问题。

## 六、沟通和口头表达专项

### 每周训练

- 3 次、每次 3 分钟录音；
- 1 次 90 秒进度汇报；
- 1 次 60 秒 Bug/风险汇报；
- 1 次 5 分钟项目 Demo；
- 周末选择一段转写稿，删除无意义口头禅和实现流水账。

### 固定结构

需求复述、进度、Blocker、Bug 和 Demo 的唯一标准格式维护在[项目管理与汇报模板](../../templates/项目管理与汇报模板.md)。本计划只安排训练频率，不再复制另一套格式，避免长期出现多个版本。

### 量化检查

- 前 20–30 秒是否出现结论；
- 是否在规定时间内结束；
- 是否说明对业务或决策的影响；
- 是否提出明确请求或下一步；
- 是否存在三个以上连续“然后、就是、那个、嗯”；
- Demo 是否提前关闭无关窗口、固定页面顺序并准备备用材料。

## 七、业务理解和结果意识专项

每周选择一个项目或公开产品，输出一页 Business Brief：

1. 用户是谁，在哪个决策点遇到什么问题；
2. 当前流程和 Baseline 是什么；
3. 公司或团队真正关心哪个业务指标；
4. 算法/Agent 通过什么机制改变用户或运营行为；
5. Primary、Secondary 和 Guardrail Metric；
6. 数据来源、粒度、时间和 Owner；
7. 怎样验证因果，不能验证时怎样限定结论；
8. 失败或无收益时如何停止、降级或回滚。

三个滴滴项目的练习重点：

| 项目 | 已有强证据 | 必须补想清楚的业务层 |
|---|---|---|
| 时效预测 | MAE、Spearman、分桶、分城、线上线下一致性 | 扫码拦截、工单完成、用户等待、运营干预及归因 |
| 阈值系统 | 金标正确率、延迟、结构化稳定性、安全执行链 | 单次配置耗时、使用人数、采用、错误率、节省人时 |
| 城市诊断 Agent | 执行底座和架构设计 | 谁使用、诊断时长、建议采纳、异常恢复、错误建议护栏 |

待补指标只是未来验证设计，不能反向写成已有成果。

## 八、Ownership 和主动汇报专项

### 每个任务开始前

必须能够复述：

- Why：为什么现在做；
- User：谁使用；
- Goal：什么结果算成功；
- Scope：做什么、不做什么；
- Metric：怎样判断好坏；
- Deliverable：最终交付什么；
- ETA：里程碑和完成时间；
- Dependency/Risk：依赖谁、哪里可能失败。

### Blocker 升级规则

- 首次发现：记录影响、已尝试动作和下一检查点；
- 影响质量、范围、安全或承诺日期：当天同步；
- 依赖其他人或团队：明确 Owner、请求、期望时间和备用方案；
- 到检查点仍未解除：主动升级，不重复发送“帮忙看看”；
- ETA 改变：同步新 ETA、原因、影响和恢复方案。

“半天/一天必须升级”只能作为默认参考。真正触发条件是它是否开始影响决策或承诺，而不是机械等待固定时长。

### 项目结束

- 上线前明确效果数据由谁提供、什么时候看；
- 日历中预留效果回看日期；
- 即使无提升，也给出样本、结论、原因和下一步；
- 一页复盘至少包括 Problem、Decision、Impact、Failure、Lesson 和 Next。

## 九、工程与 AI 辅助编程专项

代码能力分为两条线，不能互相替代：

### 9.1 真实工作能力

- 代码库阅读、Debug、SQL 和数据粒度；
- API、异常、测试、日志、监控和发布；
- 事务、并发、幂等、重试和回滚；
- 根据团队规范提交可维护代码。

练习方式：每周从个人 Agent 作品选择一个真实故障，完成复现、定位、修复、测试和复盘。

### 9.2 面试编码能力

- Python 语言熟练度；
- 常用数据结构和算法模式；
- PyTorch/模型组件手写；
- SQL、并发、缓存和小型系统编码。

练习方式见下一节及[题库与掌握度台账](03-题库与掌握度台账.md)。

### 9.3 AI 辅助代码检查清单

任何 AI 生成或大幅修改的代码，自己必须回答：

1. 输入、输出和不变量是什么；
2. 空值、重复、极值、超时和部分失败怎样处理；
3. SQL 的粒度、Join 基数、时间口径和单位是否正确；
4. 是否改变兼容性、事务、权限或幂等语义；
5. 日志和指标能否证明执行到了哪个阶段；
6. 测试是否验证业务语义，而不只验证代码运行；
7. 我能否不用 AI 逐段解释实现和取舍。

## 十、Agent Workflow 学习与实战计划

技术载体使用[个人 Agent 作品计划](04-个人Agent作品计划.md)。先掌握原理，再选择框架：

| 里程碑 | 学习内容 | 必须交付的证据 |
|---|---|---|
| A0 确定流程 | Workflow vs Agent、状态 Schema、终止条件 | 原生 Python 状态机、流程图、10 个用例 |
| A1 Agent Loop 与工具 | Tool Contract、权限、超时、错误分类 | 只读/写入工具分级、失败测试、人工确认 |
| A2 Context/RAG | 上下文装配、证据引用、时效 | 带路径引用的结果、Recall 测试 |
| A3 Eval/Trace | Golden Set、轨迹评分、版本和成本 | 30–50 条评测、错误 taxonomy、报告 |
| A4 安全与工程化 | Checkpoint、幂等、暂停/恢复、Injection、降级 | 恢复 Demo、重复执行测试、威胁清单、README |

推荐先用原生 Python/Pydantic 写 A0/A1，再用 LangGraph 等框架重构一次，对比框架解决了什么。不要为了简历名词直接堆 Multi-Agent。

## 十一、LeetCode 计划

目标不是“刷完 Hot 100”，而是恢复模式识别、正确实现、测试和表达。

| 周次 | 主题 | 新题数 |
|---|---|---:|
| 第 1 周 | 数组、字符串、HashMap、双指针、滑动窗口 | 10 |
| 第 2 周 | 链表、栈、队列、堆 | 8 |
| 第 3 周 | 树、DFS/BFS、二分、Top-K | 10 |
| 第 4 周 | 图、拓扑、回溯、基础 DP | 8 |
| 第 5 周 | DP、混合题、LRU/限流器等工程题 | 8 + 2 |
| 第 6 周 | 限时套题和薄弱题 | 4 |
| 第 7–12 周 | 以错题间隔复做和模拟为主；真实面试暴露新题型时再补 | 0–2 道可选 |

固定题量指前六周至少完成 48 道算法新题和 2 道工程题；第 7–12 周的可选新题不计入固定目标。[七天启动计划](01-七天启动计划.md)只在临近面试时替代正常第一周，不与本计划叠加；其中完成的题计入前六周总量。

每题固定流程：

1. 复述输入、输出和边界；
2. 5 分钟内说明朴素解和优化方向；
3. 30–35 分钟内完成代码；
4. 主动写正常、空输入、重复和极值测试；
5. 说明时间、空间复杂度及替代方案；
6. 标记独立完成、提示后完成或未完成；
7. 错题在 D+1、D+7、D+21 复做。

阶段目标：

- 第 1 周熟悉题型独立完成率达到 40%；
- 第 3 周达到 60%；
- 第 6 周达到 75%；
- 90% 已完成题能解释复杂度和失败边界；
- 连续三次 30 分钟模拟至少通过两次。

如果起始基线相差较大，以第 0 周结果调整目标，不为了数字牺牲复习质量。

## 十二、每周时间预算

### 标准档：18–20 小时/周

- Python/LeetCode：5 × 45 分钟；
- Agent 作品：3 × 90 分钟；
- 项目/业务：2 × 75 分钟；
- 表达录音：3 × 20 分钟；
- 系统基础：2 × 60 分钟；
- 模拟面试：1 × 90 分钟；
- JD、投递和周复盘：3–4 小时。

### 最低档：9–10 小时/周

- 编码：4 × 30 分钟；
- Agent：2 × 60 分钟；
- 项目/业务：2 × 45 分钟；
- 表达：2 × 15 分钟；
- 模拟面试：60 分钟；
- JD 与复盘：2–3 小时。

最低档减少数量，但不删除项目表达、编码、作品和模拟中的任何一条线。

## 十三、防止计划过载

1. 每周最多三个关键交付：一个业务/表达、一个技术、一个面试；
2. 同时进行的大任务不超过两个；
3. 阅读和视频不超过总时间 40%，其余必须形成录音、代码、图、答题或复盘；
4. 未完成任务不能整批滚入下周，只保留最影响面试的一项；
5. 连续两周项目表达低于 7 分，暂停学习新 Agent 概念；
6. 连续两次编码模拟失败，下一周每天先完成编码；
7. 距真实面试不足 72 小时，按项目 50%、JD 缺口 30%、编码 20% 准备；
8. 最后两周不追新框架，只做回放、模拟、补洞和输出；
9. 每周至少保留半天完全休息；
10. 目标是连续执行，不通过熬夜追赶计划。

## 十四、迁移到下一份工作的 30/60/90 天

### 入职 0–30 天：快速建立上下文

- 完成业务、系统、数据和协作关系四张地图；
- 主动约同方向算法、后端、产品/运营、资深业务同学各一次；
- 非简单任务开始前复述目标、DoD、指标、ETA 和风险；
- 每周固定状态同步；
- 第 4 周主动向 Leader 获取一次反馈。

验收：能在 10 分钟内讲清团队目标、流程、指标、数据和系统；地图至少经一名资深同事确认；没有静默延期。

### 入职 31–60 天：独立负责一个模块

- 自己给出方案、时间线、指标和风险；
- 对外部依赖明确 Owner、截止时间和升级路径；
- 对实现和上线验证同时负责；
- 完成一个小项目的完整复盘。

验收：至少一个模块完成“需求—方案—实现—验证—汇报”闭环。

### 入职 61–90 天：开始对业务结果负责

- 主动回看已上线项目效果；
- 区分模型、系统、采用和业务指标；
- 推动必要的数据、产品和运营协作；
- 再次向 Leader 获取反馈，与第一个月比较。

验收：能够准确说出负责模块产生了什么结果、证据是什么、还没有解决什么、下一步由谁推进。

## 十五、每周复盘只回答七个问题

1. 本周真正交付了什么，而不是看了什么？
2. 哪次表达先给了结论，哪次仍然从过程讲起？
3. 哪个业务假设经过了数据或用户确认？
4. 哪个风险在影响结果之前被暴露？
5. Agent 作品新增了什么可运行、可评测证据？
6. 编码失败的首要原因是知识、思路、实现、调试还是表达？
7. 下周只保留哪三个最重要的交付？
