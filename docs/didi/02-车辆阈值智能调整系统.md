# 车辆阈值智能调整与安全执行系统

更新日期：2026-09-04

详细评测口径见 [阈值系统 LLM 评测卡](../evidence/03-阈值系统LLM评测卡.md)。

## 1. 项目一句话

> 将运营人员的自然语言需求转换为受控的车辆阈值修改方案，通过权威实体知识、Java 规则、修改预览、人工审批和全链路审计，安全落到生产配置；同时为外部 Agent 提供收窄能力的结构化接入。

这个项目最值得讲的不是某个 Controller 或表结构，而是如何处理一个核心矛盾：

> 自然语言和模型输出可以不确定，但生产配置的作用范围、权限和结果必须确定。

## 2. 业务背景

车辆阈值决定哪些车进入换电等策略流程。运营需求通常以口语表达，例如：

> 把某城市某运营区周五 7–19 点所有车型阈值减 3。

真正执行前需要明确城市、运营区、星期/日期、时段、车型、相对或绝对修改、当前配置、影响范围和审批人。系统还要支持固定阈值、日期特例、复制时间/车型和订单工单比等不同业务语义。

因此项目不是 NL2SQL，而是：

```text
自然语言
→ 受控领域命令
→ 当前配置与影响预览
→ 人工授权
→ 确定性执行
→ 最终回查与审计
```

## 3. 我的主要工作

现有 Git、代码和评测材料可以支撑以下范围：

- 负责自然语言结构化解析和 Java 后置校验；
- 设计城市、运营区和车型的权威实体知识接入；
- 参与并逐步主导复杂阈值领域模型与更新语义；
- 补齐预查询、BPM、审批回调、写库、最终查询和审计链路；
- 修复局部车型修改覆盖整行配置等数据安全问题；
- 建设外部 Agent 的结构化入口和独立审批流程；
- 从真实日志与金标集做模型/参数评测和 Badcase 归因。

更准确的说法是“负责/主导核心业务链路”，不是“独立完成整个项目”。

## 4. 总体架构

```mermaid
flowchart LR
    A["运营自然语言"] --> B["权威城市/区域/车型知识"]
    B --> C["LLM 生成候选领域命令"]
    C --> D["Java 确定性校验"]
    D --> E["查询当前配置与影响预览"]
    E --> F["人工确认"]
    F --> G["BPM 授权"]
    G --> H["统一执行服务"]
    H --> I["分层配置写入"]
    I --> J["最终回查与审计"]

    K["外部 Agent 结构化建议"] --> L["有限字段校验"]
    L --> M["独立 BPM 授权"]
    M --> N["异步执行尝试与内部回查"]
```

两条入口不能画成已经共享同一套完整校验：人工链路具备权威实体校验、预查询和 Diff；外部结构化入口当前只做有限字段校验并进入独立审批，完整业务校验、持久化幂等和可供上游查询的执行终态仍待补齐。

### 组件分工

- LLM：理解自然语言、拆分指令、生成候选结构；
- 权威知识：提供真实城市、运营区和车型范围；
- Java：重新校验范围、格式、动作冲突和批量完整性；
- 数据库：提供当前真实配置；
- BPM：提供人工授权；
- 执行与审计：完成确定性写入，并证明最后发生了什么。

这套边界比“让 LLM 直接生成 SQL”更适合高风险配置场景。

## 5. 最有价值的技术判断

### 5.1 LLM 只负责理解，不拥有写权限

模型即使返回合法 JSON，也可能漏城市、漏条件、混淆相对/绝对修改。最终作用范围和动作必须由程序校验，写入还需要预览和审批。

### 5.2 合法 JSON 不等于业务正确

系统将多条输入拆成原子指令，并检查每个结果是否能回溯到原始指令，从而发现“请求 9 城、只返回 1 城”这类静默漏项。评测也按格式、字段、语义、完整性、延迟和安全阻断分层，而不是只统计解析率。

### 5.3 当前状态必须参与修改

相对增减、配置覆盖和车型回退都依赖数据库当前值。因此修改前先查询和展示，审批执行后再查询最终值。核心认知是：

> 解析成功、预查询成功、BPM 发起成功、审批通过和数据库生效是不同阶段。

### 5.4 配置要分层，而不是塞进一个 JSON

系统将长期基础配置、周期性人工调整和指定日期特例分开，并定义确定的覆盖顺序。这既支持复杂业务，也避免一次临时修改污染基础策略。

### 5.5 人工与 Agent 的信任边界要隔离

外部 Agent 使用独立入口、审批流程和链路标识，但复用底层查询、校验、执行和审计。上游已经提供固定结构时直接校验转换，不再经过第二次 LLM，避免字段漂移和额外延迟。

## 6. 可量化结果

以下是离线评测或真实日志回放，不是长期线上 SLA：

### 42 条领域金标

- 覆盖查询、相对/绝对调整、日期、跨午夜、复制、固定阈值、批量和缺字段；
- 共保留 239 次模型调用；
- 最终离线候选原始通过 40/42；
- Java 后置校验后语义通过 41/42；
- 0 次截断；
- 平均 11.61 秒，P95 20.21 秒。

### 43 条真实日志回放

- 候选模型严格 JSON 43/43；
- 平均延迟从 34.43 秒降到 7.17 秒，下降 79.2%；
- 一次调用业务可接受为 40/43，暴露批量静默漏项；
- 结论是需要程序化完整性校验和重试/阻断，而不是仅凭速度替换。

## 7. 三个面试主故事

### 故事一：单车型更新不能覆盖整行

一条配置记录同时保存多个车型。局部修改如果直接整体 upsert，会丢失其他车型和未知字段。解决思路是完整读取、定点修改、保留其余内容后整体回写。

能体现：领域建模、数据安全、读改写语义。

### 故事二：批量静默漏项

模型返回严格 JSON，却漏掉大部分城市。通过原子指令标识和覆盖检查把“格式正确、业务不完整”变成可检测失败，并用金标与真实日志评测模型。

能体现：LLM 评测、不确定性治理、Badcase 闭环。

### 故事三：“查到了但没生效”

将解析、预查询、BPM、审批回调、实际写入和最终查询分别记录，定位问题发生在哪一段，而不是把前端展示成功当成配置修改成功。

能体现：跨异步链路排障、可观测性和生产责任感。

## 8. 面试值得保留的技术深挖

这些细节值得准备，因为面试官很可能追问：

- 为什么不用 LLM 直接生成 SQL；
- 当前实体知识增强与通用向量 RAG 的区别；
- 怎样定义结构化输出的正确率；
- 怎样防止多城市/多动作漏项；
- 相对修改为什么必须查询当前值；
- JSON 整列 upsert 如何避免丢字段；
- BPM approved 后为什么 DB 仍可能失败；
- 重复回调、异步任务和多条件部分成功如何治理；
- 大批量展开导致 SQL 超长时，怎样定义事务和幂等；
- 为什么 Agent 上游已有 payload 后不再调用 LLM。

## 9. 当前边界

- 评测候选参数与当前代码配置不一致，必须确认实际线上模型与参数；
- 缺少正式用户数、覆盖城市、日均审批量、节省人时和长期成功率；
- 大批量 SQL 的根因已定位，但完整事务化分批治理没有被当前材料证明；
- 审批回调的持久化幂等和可靠任务恢复仍需加强；
- Agent 直传路径的实体归属校验弱于人工解析路径；
- 当前回调给上游的主要是审批结果，不能等价成 DB 最终写入成功；
- 城市异动诊断 Workflow 是下一阶段设计，不属于本项目已上线成果。
