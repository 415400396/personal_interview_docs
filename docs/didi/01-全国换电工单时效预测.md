## 1. 项目一句话

> 面向共享单车换电运维，预测工单派发后车辆下一个关键用户事件的时间，用作有限换电人力的优先级信号；我接手既有系统，推动后续模型从业务口径、数据特征和模型评估演进到 Java 服务接入与线上效果分析。

## 2. 业务背景

同一时间有大量低电、缺电或断电车辆，但换电人员和运力有限。模型要帮助判断哪些车更可能很快发生用户扫码，优先安排处理，减少因换电不及时产生的用户拦截。

Label 不是单纯的“换电完成时间”：

1. 换电完成前发生扫码拦截，取拦截时间；
2. 没有拦截，取换电完成后首个正常订单时间。

这使任务同时受用户需求、运维到达、换电完成和完成后等待首单影响，天然存在混合机制和长尾。

## 3. 我的主要工作

- 明确 Label、模型生效时段、分桶和验收口径；
- 重构日级、历史 Label 和小时级特征的时序关系，避免特征穿越；
- 完成旧 115 维特征的消融与 87 维最终特征重建；
- 使用日期 OOT、同工单、分桶和分布标准化评估模型；
- 系统比较标准回归、加权、自定义损失、校准、门控和城市分组方案；
- 在 XGBoost 0.90 Java 运行时约束下冻结可部署模型和特征契约；
- 完成线上线下向量对账、灰度对比和城市小时级效果评估。

个人边界的安全说法是“接手既有服务，负责/主导后续模型与工程演进”，不是“从零搭建整套倒计时服务”。

### 数据与时序

- 普通日级特征使用 S-1；
- 历史 Label 使用 S-2；
- 小时级特征使用 H-1 完整快照；
- 线上短 TTL 数据与训练历史回放分开；
- 半年原始特征数据为 181 日、7,829,793 行；
- 91 维候选经真实数据审计后删除 4 个全零字段，冻结为 87 维。

面试重点是解释每个时序偏移防止什么泄漏，而不是背 SQL 表名。

### 模型选择

- 结构化表格特征、数百万样本和旧 Java runtime 使 XGBoost 成为风险收益更合适的选择；
- 先用 115→50→35 维消融验证旧特征冗余，再在 35 维底座上增加实时供需与城市特征；
- 最终 custom loss 只比 linear 好约 0.25 分钟，稳定性和兼容性更重要，因此选择 `reg:linear`；
- 使用 CPU `hist` 等配置重训，固定 536 棵树和模型哈希，减少训练与线上推理差异。

不要说“做过深度模型对照并证明 XGBoost 更好”，当前材料没有这个实验。

## 5. 最值得讲的技术判断

### 5.1 用未来 OOT 否定随机集的漂亮结果

短时 P25 优化在随机 test 上明显提升，但未来日期 OOT 没有形成稳定替换价值，而且长尾退化。由此将“局部达标、全量效果、未来泛化”分开评价。

### 5.2 发现 MAE 75.60 是假改善

一次新标签口径试验中，MAE 从旧模型约 132 降到 75.60。进一步分析发现，不同表中相同事件类型编码的业务含义发生变化，6–12 小时长尾样本占比大幅下降。

通过分桶贡献、交叉重加权和同工单对照证明这不是模型能力跃升，随后重新确认业务事件、删除错误 run 并重训。

这是项目最强的技术判断案例：先怀疑过于好看的结果，再证明它为什么错。

### 5.3 城市差异存在，但不代表值得拆模

活跃车车均单与城市 Label P25 相关明显，但高/中/低三组模型真实路由只改善 0.1165 分钟，短桶还有退化。最终保留全国模型，避免为极小收益增加多模型维护成本。

### 5.4 稳定交付优先于微小离线收益

在旧版 XGBoost Java 运行时约束下，选择易兼容的 linear 模型，并把特征顺序、树数、模型文件和在线向量都固化验证，而不是只交付一个离线分数。

## 6. 最可靠的结果

### 严格同工单对照

样本：318,499 单、228 城。

| 指标 | 旧线上 115 维基线 | 最终 87 维候选 | 变化 |
|---|---:|---:|---:|
| MAE | 126.84 | 123.91 | -2.93 分钟，-2.30% |
| RMSE | 202.75 | 198.03 | 改善 |
| Spearman | 0.4965 | 0.5280 | 提升 |
| 严格通过率 | 30.82% | 30.90% | 基本持平 |

- 228 城中 196 城 MAE 改善；
- 主要收益来自 2 小时以上和长尾排序；
- 30–60 分钟桶 MAE 退化 6.03 分钟；
- 正式全量/逐城 80% 目标没有达到。

所以最稳妥的结果表述是：

> 最终候选在公平同样本上降低总体误差并改善多数城市，收益主要位于长时段；短时桶存在代价，严格通过率基本持平。

### 工程与评估交付

- 87 维、536 树的 CPU 模型及固定特征契约；
- 同一完整特征向量下，线上/本地预测差异为 0.39945 分钟；
- 217 城、62 天、347,292 行、110 列的城市小时级评估集；
- 新旧模型灰度对比、分城市/时段风险识别和配置化回退能力。

## 7. 三个面试主故事

### 故事一：推翻错误的模型突破

从 MAE 75.60 出发，通过分桶、分布标准化和同工单对照定位 Label 语义迁移。体现数据敏感度、实验设计和对结果负责。

### 故事二：线上线下预测差异

一次线上/本地差 9.11 分钟，逐层核对模型文件、树数、特征顺序和同次完整向量，最终证明同向量只差 0.399 分钟，原差异来自不同 Redis 快照。体现算法工程和跨栈排障。

### 故事三：为什么不用更复杂的模型

custom loss、城市拆模和长尾门控有局部收益，但综合旧运行时、分桶代价、维护成本和可解释性后选择稳定 linear。体现技术选型而非排行榜思维。
