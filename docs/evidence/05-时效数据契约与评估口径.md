# 时效预测：数据契约与评估口径

更新日期：2026-09-04

本文由三份原始评估 SQL 静态审阅后脱敏重写。原 SQL 仅用于本机核验，不进入个人 Git；本文不包含真实库表名、字段名、城市范围、车辆/工单标识或内部业务状态码。

## 1. 一条样本的时间轴

```text
工单派发时间                 线上预测请求 T0                    T0 + 24h
     |---------------------------|--------------------------------|
     |                    此前信息可作特征                此后事件只作 Label/评估
```

必须明确两组时间：

- `feature_cutoff = T0`：任何模型输入的事件时间必须早于或等于该截点；
- `observation_window = [T0, T0 + 24h]`：未来完成、订单或扫码事件只用于后验标签和评估。

当前 SQL 中观察窗以请求时间为锚点，而时长 Label 可能以工单派发时间为起点。两者不一定相同，必须在正式模型卡中明确，并检查延迟请求是否造成系统性偏差。

## 2. 一行一工单

目标粒度：每个被评估工单保留一次明确的预测快照。

建议规则：

1. 明确取首次、末次还是固定阶段预测；
2. 排序使用稳定的二级键，避免相同时间戳下结果不确定；
3. 每类未来事件只保留观察窗内最早合法事件；
4. 维表 Join 前先保证业务键唯一；
5. Join 后断言 `count(*) == count(distinct sample_id)`；
6. 若允许一工单多快照，样本主键必须显式包含快照时刻。

`distinct` 计数只能掩盖部分重复，不能阻止均值和分位数被重复行放大。

## 3. Label 契约

一个可迁移的 Label 文档至少包含：

- 候选目标事件集合；
- 多事件同时出现时的优先级；
- 完成、取消、超时、无事件和数据异常的状态；
- 时长的开始与结束时刻；
- 24 小时观察窗结束后的右删失/截尾处理；
- 负时长、超窗、重复和同秒事件的规则；
- 训练 Label 与监控 Label 是否完全相同。

当前脚本将部分“观察窗内无有效事件”样本按 24 小时截尾。此时计算的是截尾成本或惩罚，不应叫作“平均完成时长”。取消时间虽存在于数据中，但是否参与目标事件选择需要本人再次核对。

## 4. 关联键强度

从强到弱：

1. 同一工单的直接事件键；
2. 工单与车辆、城市、时间窗的复合键；
3. 仅车辆 + 城市 + 时间窗。

使用弱键关联未来订单/扫码事件时，可能把同一车辆后续其他业务过程错配给当前工单。必须统计：

- 每个样本候选事件数量；
- 多候选率；
- 无候选率；
- 时间重叠与相邻工单比例；
- 随机抽样人工核对结果。

面试中可以将其概括为：业务事件配对不是普通 Join，需要显式建模“谁属于谁”和 point-in-time 正确性。

## 5. 单位与缺失契约

每个字段必须注明：

- 原始单位：秒、毫秒、分钟、小时或比例；
- 转换发生在哪一层；
- 缺失与真实 0 是否可区分；
- 默认值、截断范围和异常处理；
- 不同模型/历史版本是否曾使用不同单位。

严禁用一个“远未来时间戳”替代未完成样本后，再与小时数一起计算分位数。若需要惩罚，使用显式 `censored_duration=24h` 和 `is_censored`，并分开报告。

## 6. 监控窗口

当前三份 SQL 反映的主要口径：

- 日指标：D-1；
- 滚动周：D-7 到 D-1，共 7 个完整自然日；
- 高峰：请求小时 15–22，即 `[15:00, 23:00)`；
- 汇总层级可能包含全国、城市、区域和时段。

每个聚合行的唯一键应由“统计周期 + 时段 + 地理层级 + 必要业务维度”构成。外部上下文、扫码和主样本 Join 时必须先聚合到同一键，并检查一对一。

## 7. 五层评估框架

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| Outcome | 业务最后发生了什么 | 完成/取消/未完成、倒计时内完成率 |
| Monitor | 是否延续历史监控口径 | Label/预测分位数、阈值累计量 |
| Diagnostic | 模型为什么好或坏 | MAE、过估/低估比例与幅度、缺失率 |
| Context | 时期是否可比 | 订单、供需、天气、城市经营背景 |
| Quality | 数据能否相信 | 分区完整、重复、冲突状态、Join 放大 |

把五层指标放在同一宽表可以方便分析，但不能混成一个结论。环境上下文用于解释可比性，不是模型效果本身。

## 8. 分母必须写清

同一个“完成率”可能有不同分母：

- 全部工单；
- 有合法 Label 的工单；
- 24 小时内已完成工单；
- 某个真实 Label 分桶；
- 某个预测分桶；
- 同工单对照集。

每个比例都要处理分母为 0，并同时记录 numerator、denominator 和 rate。只保存 rate 会让后续无法判断小样本波动。

## 9. 后验分层与因果边界

使用真实 Label 的 P25 选择“短时工单”适合事后诊断，但它是 outcome-conditioned cohort：线上决策时并不知道未来真实 Label，因此不能直接用来证明模型对前瞻业务策略的收益。

同样，上线前后比较如果同时发生天气、订单、供给、城市结构或样本口径变化，也不能直接归因给模型。更可靠的顺序：

1. 同样本离线比较模型能力；
2. shadow 验证服务一致性；
3. 有控制的灰度或同期对照；
4. 同时报告环境与数据质量；
5. 区分描述性变化和因果结论。

## 10. 建议的数据质量断言

```text
分区连续且数据新鲜
sample_id 唯一
Join 前后行数变化在预期内
事件时间 >= 合法起点且 <= 观察窗终点
特征 event_time <= feature_cutoff
所有时长单位已统一为分钟
所有比例 numerator <= denominator 且 denominator > 0
完成/取消/未完成状态互斥或有明确冲突标记
预测缺失率、Label 缺失率和截尾率分别统计
每个聚合键最多一行
```

## 11. 这三份 SQL 能证明什么

可以证明的工程深度：

- 将线上预测与未来业务事件做 point-in-time 对齐；
- 同时建设日/周、分时段、多地理层级监控；
- 将业务结果、旧监控、模型诊断、环境和数据质量分层；
- 意识到 Label、分母、单位、Join 基数和因果边界是模型评估的一部分。

不能据此新增的简历结论：

- 新的覆盖城市、调用量或业务收益；
- 某个模型上线必然导致指标改善；
- SQL 中所有风险已经修复；
- 原始 SQL 或数据可公开。
