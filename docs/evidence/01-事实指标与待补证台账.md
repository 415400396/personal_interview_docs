### 2.2 最强技术事实

- 重新核验混合事件 Label，并识别同一事件类型编码在不同数据源中的业务语义迁移。
- 对“MAE 约 132 → 75.60”的异常漂亮结果做分布重加权，证明主要是长尾样本比例变化造成的伪提升。
- 使用按日期 OOT、同工单、公平分桶和分城分析，避免随机切分与样本结构掩盖问题。
- 完成 87 维特征契约、旧 Java 运行环境接入和线上/离线输入对账。

### 3.3 可确认工程事实

- LLM 负责把模糊表达转换为领域命令，不直接生成或执行 SQL。
- 实体知识限定城市和运营区范围；数据库提供当前状态；Java 拥有字段、范围、互斥、批量完整性和更新语义的最终判断。
- 高风险修改经历预查询/影响预览、人工确认、BPM、审批回调、确定性执行和审计。
- 人工入口与外部 Agent 的结构化入口隔离；上游已有固定 payload 时不再调用 LLM 二次生成。
- 已定位大批量展开造成的 SQL 长度失败，但事务、拆批、重试和幂等方案尚未形成可证明的完整上线闭环。

### 4.1 规划数字不是成果

[评测、灰度、SLO 与量化目标](../city-agent/04-评测灰度SLO与量化目标.md) 是城市 Agent 正式评测 KPI、样本门槛、SLO、容量目标、发布 Go/No-Go 和业务改善数字的唯一权威来源；这些数字全部是【规划门槛】或【预期目标】，当前【实际结果】均为“暂无”。其他设计文档中的工具预算示例和安全不变量不构成实绩或独立验收口径。

未来只有同时补齐以下信息，才可把一个规划数字迁移到本台账的 A/B 级结果：

1. 评测/灰度时间与 Agent、Prompt、工具和指标口径版本；
2. Episode、Scope 和关键根因/严重度切片的样本数；
3. 人工、规则版本、上一版本或同期控制的对照；
4. 实际 Baseline、结果、效应量、置信区间和 Guardrail；
5. Critical Badcase、拒绝、编辑、回滚和适用边界；
6. 可复算报告、Dashboard 或脱敏审计证据。

## 5. 滴滴个人贡献证据

现有代码、历史和项目材料可以辅助证明本人对结构化解析、阈值执行、BPM、实体知识、外部 Agent 接入和审计等环节有实质贡献，但暂不能据此推导“独立完成整个系统”或精确贡献比例。

长期仓库不保存个人提交数、仓库总行数、模块行数比例或 `git blame` 百分比：这些数字受分支、合并和重构影响，既是弱 ownership 证据，也没有面试表达价值。正式面试应由本人确认负责范围、关键决策、协作对象和验收方式，用可复核交付说明贡献。

## 7. 使用检查

一条新表述只有在能回答以下问题时才能升为 A/B 级：

1. 指标对象是什么：行、工单、请求、城市还是审批？
2. 样本来自哪段时间，是否经过筛选？
3. 对照是谁，是否同样本、同时段、同配置？
4. 是离线、回放、灰度还是长期生产？
5. 是模型裸结果，还是规则/Java 后处理后的系统结果？
6. 结果是否有反例、失败样本和适用边界？
7. 本人是主导、独立负责、共同完成还是局部参与？
