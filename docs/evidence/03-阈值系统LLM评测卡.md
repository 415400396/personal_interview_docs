# 车辆阈值系统：LLM 评测卡

更新日期：2026-09-04

本文保留“模型为什么被选择、系统为什么需要确定性校验”的证据。它不是生产 SLA 报告，也不保存原始用户输入、Prompt、日志或模型推理内容。

## 1. 任务定义

输入是运营人员的自然语言查询或修改意图，输出是受 Schema 约束的领域命令。正确性不只看 JSON 是否可解析，还要求：

- 城市、运营区、车型、日期、星期和时段合法；
- 查询与修改意图不混淆；
- 相对/绝对调整、复制、比例和固定阈值等动作语义正确；
- 批量指令中的目标不能静默遗漏；
- 缺少必填条件时进入补全，不擅自猜测；
- 最终结果能被 Java 规则安全消费。

## 3. 基线对比

相同原始 Prompt、4,000 tokens：

| 模型 | 业务金标通过 | 截断 | 平均延迟 | P95 | 最大 |
|---|---:|---:|---:|---:|---:|
| 原基线 | 29/42（69.0%） | 10 | 21.23s | 52.31s | 61.27s |
| 候选基线 | 36/42（85.7%） | 2 | 13.80s | 23.01s | 46.68s |

仅提高原基线的 token 上限没有解决根因：10 条失败用例中只有 1 条恢复，6 条再次耗尽 token，平均 69.41 秒、最大 101.06 秒。这说明“给更多 token”不是可靠的结构化任务修复策略。

## 6. 真实日志回放

样本时间：2026-08-04 至 2026-08-10，共 43 条真实 LLM 请求。候选模型使用相同 Prompt 离线回放。

原始导出共 253 条逻辑记录，其中 43 条为实际模型请求（实体解析 21、业务指令解析 22），另有 208 条执行审计和 2 条空/异常记录。评测只把 43 条模型请求作为模型回放分母，没有把执行日志误算成模型样本。

| 指标 | 原模型日志 | 候选模型回放 |
|---|---:|---:|
| 请求/解析成功 | 41/43 | 43/43 |
| 严格 JSON | 20/43 | 43/43 |
| 清洗后可解析 | 41/43 | 43/43 |
| 平均延迟 | 34.43s | 7.17s |
| P50 | 20.93s | 5.47s |
| P90 | 77.18s | 13.03s |
| P95 | 78.16s | 15.66s |
| 最大延迟 | 129.23s | 22.30s |
| 一次调用业务可接受 | 41/43 | 40/43 |

候选平均延迟降低 79.2%，总耗时由 1,480.50 秒降到 308.44 秒，43/43 都比对应原请求快。但它出现批量静默漏项：有请求漏掉列表项，也有多城市请求只返回一个城市。

两条失败样本各复跑两次均恢复；加一次重试后的观察结果为 42/43、平均 7.96 秒。由于这只是对已知失败样本的离线复测，不能当长期 SLA。

## 7. 评测得出的系统设计结论

1. 严格 JSON 只证明格式，不证明业务正确。
2. 批量完整性必须由程序比较“请求目标集合”和“输出目标集合”。
3. 字段范围、动作互斥、实体归属和缺失补全必须由确定性规则兜底。
4. 重试只适合瞬时和非确定性失败；非法输入、越权和规则冲突不应盲目重试。
5. 需要按错误类型分别统计：格式、Schema、语义、漏项、知识不匹配、延迟、截断和系统异常。
6. 模型选择应联合考虑任务成功率、P95、长尾失败和执行风险，而不是单看平均延迟。

## 8. 不能混淆的口径

- 离线金标 41/42 ≠ 生产长期准确率；
- 日志离线回放 ≠ 同期线上 A/B；
- 43/43 严格 JSON ≠ 43/43 业务正确；
- 重试观察 42/43 ≠ 已上线重试后的 SLA；
- 离线候选参数 ≠ 后续代码或生产实际参数；
- 模型通过率 ≠ 审批通过率、写库成功率或业务收益。

当时离线全量的候选配置与后来代码快照中的 token 上限和 top-p 不一致。在确认部署版本与变更原因前，只能说“离线评测得到候选结果”，不能说“线上长期使用该参数并达到 97.6%”。

## 9. 下一版评测应补什么

- 按真实流量分层采样，扩展到至少数百条可持续回归集；
- 双人标注、分歧仲裁和标注规范；
- 解析、预览、审批、执行、回查各阶段独立指标；
- 批量目标覆盖率和字段级准确率；
- 越权、Prompt 注入、伪造实体和高风险修改的红队集；
- 线上 shadow/灰度、版本对照和回滚门槛；
- 采纳率、用户修正次数、节省耗时与最终业务效果；
- 生产 P50/P95/P99、重试率、成本和失败漏斗。
