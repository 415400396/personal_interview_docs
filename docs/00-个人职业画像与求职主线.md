# 个人职业画像与求职主线

更新日期：2026-09-04

## 1. 先给结论

最适合我的职业定位不是“会很多模型的泛 AI 工程师”，而是：

> **具备算法研究底座，能够把不确定的模型能力转化为可评测、可约束、可上线业务系统的 AI 应用 / Agent 工程师。**

这条主线能把三段经历连起来：

- 在 USC ICT 做生成模型和人体动作研究，形成问题建模、论文实验和模型评估能力；
- 在南湖研究院做大模型应用、JAX/ONNX、MoE 路由与推理适配，补上模型框架和部署视角；
- 在滴滴把机器学习、数据链路、Java 服务、LLM/RAG、审批和线上评估真正接入高风险业务流程。

真正有区分度的不是“同时会 Python 和 Java”，而是能在以下两类系统之间建立可靠接口：

1. **概率系统**：模型预测、LLM 理解、诊断假设都可能出错；
2. **确定性系统**：数据口径、字段校验、权限、审批、幂等、数据库写入和审计必须明确。

## 2. 我的职业演进

### 2.1 研究阶段：学会定义问题和证明结论

USC ICT 的工作重点是生成模型、人体动作与视频理解。可沉淀的能力不是单纯“发过论文”，而是：

- 将一对多的动作生成问题转化为离散表示与生成建模问题；
- 围绕 VQ/RQ-VAE、离散扩散等方法设计可复现实验；
- 同时使用客观指标和用户研究评估生成质量；
- 处理论文写作、消融、失败实验和同行审查；
- 以 IROS 2023 第一作者、BMVC 2023 第二作者提供研究能力证据。

这段经历解释了为什么后来做业务模型时，我会主动怀疑“过于好看”的离线结果，并用 OOT、同样本和分桶归因验证，而不是只接受一个总分。

### 2.2 框架与部署阶段：理解模型如何进入工程系统

南湖研究院的价值在于从“训练一个模型”向“让模型能迁移、能推理、能服务”扩展：

- 参与 Qwen MoE 路由、SNN 阈值思路及 CUDA/Triton、vLLM 适配；
- 基于 JAX 建设模型开发与转换能力，涉及 JAX 到 ONNX、算子兼容和部署验证；
- 在 CBT 场景中将领域流程、角色分工、RAG、数据生成和阶段化 SFT 串成多智能体数据流水线。

这段经历可以证明我理解模型结构和推理约束，但正式面试前还需要补充本人在每个模块的准确责任、实际交付状态和可量化结果，避免技术名词过多而个人贡献不清。

### 2.3 业务落地阶段：形成端到端闭环能力

滴滴三个项目把前两段能力落在真实业务约束中：

- **时效预测**：从 Label、SQL、时序特征、XGBoost 训练做到 Redis/Apollo/Java 对账、灰度和线上效果评估；
- **阈值系统**：从自然语言理解做到权威实体知识增强、Java 校验、三层配置合并、预查询、BPM、回调落库和审计；
- **城市诊断 Agent**：在已有执行底座上完成证据驱动 Workflow、MCP 工具、规则护栏和人机协同的下一阶段设计。

这里形成了我的核心方法论：

> 模型负责提出高价值候选，程序负责验证事实与边界，人负责授权高风险动作，日志和评测负责证明最后发生了什么。

## 4. 三个最强的个人标签

### 标签一：能够治理 AI 的不确定性

我并不把“用了 LLM”当成项目价值。更重要的是把不确定性逐层收敛：

- 权威知识和主数据提供事实边界；
- LLM 负责理解和候选结构；
- Java 重算缺失、范围、互斥和完整性；
- 预查询展示实际影响；
- BPM 保留人工授权；
- 最终回查与审计证明写入结果。

这比“Prompt 调得好”更接近企业真正需要的 Agent 工程能力。

### 标签二：能从数据到服务完成闭环

时效项目证明我不只在 notebook 里交付模型：

- 设计无穿越时序特征；
- 用 OOT 和同工单评估；
- 冻结特征顺序与模型哈希；
- 对齐 Redis 片段、Java 拼接和 XGBoost 版本；
- 建设城市/小时级上线评估；
- 设计灰度、监控和回退机制。

### 标签三：愿意推翻漂亮但错误的结论

两个代表案例：

- 一次新标签口径的结果显示 MAE 从约 132 降到 75.60，最后确认是事件类型编码的业务语义变化改变了长尾占比，没有把它包装成模型突破；
- 模型上线前后城市评估没有看到一致显著改善，也没有把描述性变化说成因果收益。

这体现的是工程和研究共同需要的可信度意识。

## 5. 适合优先投递的岗位

### 第一优先：AI 应用 / Agent 工程师

匹配点：

- 不止会调用模型，还做过结构化输出、RAG、规则、Workflow、审批、回调和评测；
- 有 Java/Spring 的企业系统能力，适合高风险、强流程、内部工具和行业 Agent；
- 知道 MCP、Function Calling、Workflow 各自解决什么问题，也知道哪些能力尚未上线。

需要补强：持久化状态机、消息队列、幂等、在线评测与工具权限治理的实战证据。

### 第二优先：应用型 Agent 平台 / AI 平台

匹配点：

- 有领域模型、工具契约、审批、审计和外部 Agent 接入经验；
- 能用 Java/Python 连接模型、数据与业务服务；
- 对状态、可靠执行、权限和可观测性有真实问题经验。

需要补强：持久化状态、消息队列、幂等、Context/Memory/Harness 和平台规模证据。只投应用 Runtime/平台型岗位，不把虚拟化、存储网络型 Agent Infra 混进来。

### 第三优先：算法工程 / 业务机器学习

匹配点：

- 有完整的表格模型、时序特征、实验设计和线上效果评估经验；
- 能把离线模型交付到旧版 Java runtime；
- 对数据口径、泄漏和伪提升较敏感。

需要注意：正式业务目标未全面达成，卖点应是可信评估、长尾改善与工程交付，而不是夸大全量业务收益。

## 6. 不应把自己包装成什么

- 不宜包装成纯 LLM 算法研究员：最近最强证据在 Agent 工程和业务闭环，不是基础模型预训练。
- 不宜包装成纯 Java 后端：会掩盖模型、实验设计和研究经历的差异化。
- 不宜声称“全自动自治 Agent”：当前高风险动作依赖人审，城市诊断 Workflow 尚缺上线证据。
- 不宜声称时效模型“全面达标”或“全桶提升”：正式全量/逐城 80% 未达到，30–60 分钟桶还有退化。
