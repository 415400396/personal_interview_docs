## 一、整体结论

这一年不是“技术做得很差”，也不是“只差一点表达技巧”。更准确的结论是：

> 我完成了从研究和算法原型走向真实业务系统的第一次转换，但工作模式仍偏技术执行者，尚未稳定形成以业务目标、跨团队推进和结果闭环为核心的 Owner 工作方式。

我已经证明自己可以学习并完成跨栈任务：业务 SQL、时序数据、XGBoost、Java 服务、LLM 结构化输出、规则校验、BPM 审批和 Agent 接入。但公司评价一个项目，不只看“模型和代码是否完成”，还看：

1. 是否快速理解了真正的业务问题；
2. 是否在开始前对齐完成标准和指标；
3. 是否让相关人持续知道进度、结果和风险；
4. 是否主动推动依赖，而不是等待条件成熟；
5. 是否证明系统最终改变了业务指标或工作效率；
6. 是否把经验沉淀为团队下一次可以复用的资产。

这六点正是我这一年没有稳定做好的部分。

因此，下一阶段不是单纯“多学几个框架”或“多刷一些题”，而是完成一次工作操作系统的升级：

```text
以前：接任务 → 自己研究 → 做出代码/模型 → 等别人查看

以后：理解业务 → 对齐目标与指标 → 拆解计划 → 推动依赖
      → 交付与验证 → 主动同步 → 拿到效果 → 复盘沉淀
```

## 二、这一年真正获得了什么

### 2.1 第一次看见完整的生产链路

过去更熟悉的是：

```text
Dataset → Model → Metric → Paper / Deliverable
```

这一年开始面对：

```text
Business → Data → Algorithm → Engineering → Deployment
         → Monitoring → Operation → Impact
```

这让我真正理解：模型只是链路中的一个环节。Label 错了、数据时点泄漏、线上线下输入不一致、审批回调失败、结果没有被业务采用，都会让一个离线指标不错的项目失去价值。

### 2.2 形成了值得保留的能力

- **对指标可信度敏感**：在时效项目中识别了样本分布变化造成的异常漂亮结果，没有把伪提升写成成果。
- **能跨越模型与工程边界**：从 SQL、训练和评估走到旧版 Java 环境的模型接入与线上对账。
- **理解 AI 的风险边界**：在阈值系统中让 LLM 负责理解，Java、权限、审批和审计负责确定性约束。
- **能做诚实的负结果分析**：城市拆模收益不足、短时桶退化、候选模型速度变快但业务可接受率没有同步提高，都没有被隐藏。
- **后期适应速度已经改善**：领导反馈并非认为我一直没有进步；SQL、工程环境和交付速度在后期已有提升。

这些能力说明我的技术基础和学习能力不是主要瓶颈。真正限制产出的，是没有把这些能力稳定组织成面向业务结果的工作闭环。

### 2.3 这份复盘怎样使用反馈

文中的判断分成三层，不应混为一谈：

- **直接反馈**：业务和系统熟悉较慢、主动汇报不足、需求应完整复述、风险要及时暴露、两个项目缺少效果闭环、口头表达和 Demo 需要改善、AI 代码必须自行验证；
- **项目证据**：已有技术指标、工程链路，以及当前缺失的业务指标，来自本仓库项目文档和事实台账；
- **个人解释**：“工作模式偏技术执行者”“受研究型惯性影响”等是我对上述事实的归因，不是领导的原话，也需要在后续实践中继续检验。

这样做是为了认真接住反馈，同时避免把一次阶段性表现扩大成固定的人格判断。

## 三、领导反馈指向的五类核心问题

### 3.1 业务理解和进入上下文的速度偏慢

#### 具体表现

- 接到需求后才按需查询局部背景，没有优先建立完整业务地图；
- 对核心流程、数据表、指标、上下游系统和负责人不够熟；
- 不熟悉时倾向于自己继续查，主动向产品、运营、后端和资深同学提问不足；
- 有时先形成技术方案，再补问业务为什么需要它；
- 容易把模型指标当作最终目标，没有提前连接到业务动作和业务指标。

#### 造成的后果

- 同样的任务需要更长时间定位数据、代码和口径；
- 可能解决了技术问题，却没有解决业务最在意的问题；
- 方案中出现“想当然”的假设，后期才返工；
- 难以及早判断某个模型提升是否值得上线。

#### 更准确的自我判断

这不是“理解能力差”，而是业务学习方式过于被动。过去习惯围绕任务补知识，下一阶段必须在进入团队时主动建立业务、系统、数据和人员四张地图。

### 3.2 沟通、口头表达和主动汇报不足

#### 具体表现

- 回答问题时容易从排查过程讲起，没有先给结论；
- 讲话边想边说，主线、信息顺序和时间节点不够清楚；
- 默认听众知道背景，技术细节多于对方真正需要的信息；
- 做了工作以后等待上级询问，没有固定同步进度、结果、风险和下一步；
- Demo 时页面切换、鼠标移动和临场组织过多，削弱重点。

#### 造成的后果

- 对方需要自己从大量细节里寻找答案；
- 组织无法及时判断项目是否走在正确方向；
- 即使实际做了很多，产出和价值也可能不可见；
- 风险暴露过晚，会让延期看起来像突然发生。

#### 更准确的自我判断

沟通不是性格外向，也不只是“说得流畅”。它是一种项目控制能力：让决策者及时获得结论，让协作者明确依赖，让风险在还能处理时被看见。

### 3.3 结果意识不足，不会主动“拿效果”

#### 具体表现

- 容易把代码合并、模型上线或接口跑通当作项目完成；
- 项目开始时没有同步设计 Primary、Secondary 和 Guardrail Metric；
- 离线模型指标较完整，但业务指标、采纳率、节省人时和长期 SLA 缺少跟踪；
- 上线后容易转入下一个任务，没有在合理观察窗口后主动追回效果；
- 总结时更习惯描述做了什么，而不是业务因此发生了什么变化。

#### 造成的后果

- 时效项目能证明 MAE、排序和分桶变化，却缺少拦截率、履约或运营动作的因果闭环；
- 阈值系统能证明解析质量和延迟，却缺少实际使用人数、操作耗时、错误率和采纳率；
- 技术交付真实存在，但上级难以把它转换成清晰的业务产出。

#### 更准确的自我判断

“不会拿效果”不等于没有做出东西，而是没有把效果设计、数据获取和结果汇报当成项目本身的一部分。以后不能等上线后再问怎样评估。

### 3.4 项目管理和 Ownership 不够成熟

#### 具体表现

- 需求开始前，没有稳定确认目标、范围、交付物、指标、ETA、依赖和风险；
- 卡住时先长时间独立解决，担心过早暴露问题；
- 依赖运营、产品或其他团队时，推进和催办不够主动；
- 没有固定里程碑和决策记录，方向偏差可能到较晚才发现；
- 对“最终指标是否拿到”承担得不够彻底。

#### 造成的后果

- 上级可能默认项目没有风险；
- 跨团队依赖变成隐形延期；
- 一周后才发现方向不一致，前期投入浪费；
- 项目完成边界停留在个人任务，而不是业务结果。

#### 更准确的自我判断

Ownership 不是一个人包办全部工作，也不是无限加班。它是对目标持续负责：知道谁能解决什么、什么时候需要升级、怎样让项目向结果移动。

### 3.5 工程环境适应和 AI 辅助验证还需加强

#### 具体表现

- 前期对 Java、SQL、内部平台、发布和监控不熟，影响交付速度；
- 没有在第一周系统阅读团队的目录、日志、异常处理、测试、配置和发布规范；
- 使用 AI 辅助编程时，需要更严格检查 SQL 粒度、Join、空值、时间口径、兼容性和失败路径；
- 容易把“编码速度”与“整体交付速度”混在一起，没有先定位真正的慢点。

#### 更准确的自我判断

不能把问题粗暴总结成“代码能力差”。更准确的是：工程环境适应速度、代码库阅读方法和验证闭环不足。后期速度提升证明这些是可以通过方法训练改善的。

## 四、三个项目怎样映射这些反馈

| 项目 | 已经做好的事情 | 暴露出的核心不足 | 下一次应怎样做 |
|---|---|---|---|
| 全国换电工单时效预测 | Label 审计、OOT、同工单评估、分桶和分城分析、Java 对账 | 技术指标完整，但业务动作指标和因果效果不足；未在立项时固定指标树 | 同时定义模型、服务、运营动作和业务四层指标；上线前确认数据 Owner 和效果观察日期 |
| 车辆阈值智能调整系统 | LLM、实体知识、Java 校验、预览、审批、执行、审计和离线评测形成主链 | 解析与延迟有证据，采纳率、节省人时、生产成功率和长期 SLA 不足；批量写风险闭环不完整 | 立项时记录人工基线耗时、使用量、错误率和失败状态；为持久化幂等与最终状态设置验收门槛 |
| 城市异动诊断 Agent | 能从执行底座推导完整的诊断 Workflow、安全和评测设计 | 架构设计容易被误写成项目成果；缺少实现、用户、调用和效果证据 | 明确 POC、试点、上线和效果验证四个状态；每升一级都要求对应证据 |

三个项目共同说明：我不是没有技术产出，而是需要更早回答四个问题：

1. 谁会因为这个项目改变行为？
2. 哪个业务指标会改变？
3. 怎样证明变化来自这个项目？
4. 如果指标没有变化，何时停止、回滚或换方案？

## 五、这些问题背后的根因

### 5.1 研究型工作惯性

过去习惯先把问题研究清楚，再给出完整结果；业务环境更需要在信息不完整时分阶段对齐。长时间独立探索会降低组织反馈速度。

### 5.2 把提问误解成能力不足

遇到陌生系统时倾向于自己解决，希望先形成完整理解再请教。事实上，高质量提问是缩短上下文获取时间，前提是先做最小调查并带着明确问题找对人。

### 5.3 Definition of Done 过早结束

默认的完成标准偏向“代码完成、模型完成、测试完成”，缺少灰度、采用、业务效果、复盘和文档。

### 5.4 没有建立固定的外部节奏

汇报、风险同步、效果回看依赖临时想起，而不是由固定模板和日历触发。仅靠意志力很难长期改变。

### 5.5 技术细节提供了安全感

讨论实现细节通常有明确答案；讨论业务目标、跨团队推进和不确定结果更模糊。因此容易在自己擅长的技术区投入过多，而延后需要沟通的部分。

## 六、以后如何定义一个项目真正完成

```text
1. Problem       业务问题、用户和当前损失是什么
2. Baseline      当前模型、流程和业务指标是多少
3. Goal          目标值、时间窗口和约束是什么
4. Scope         做什么、不做什么、由谁负责
5. Solution      为什么选择这个方案
6. Offline Eval  离线是否值得进入下一阶段
7. Online Eval   服务、采用和业务指标怎样验证
8. Rollout       是否放量，何时回滚
9. Impact        最终取得什么结果，证据在哪里
10. Postmortem   失败、经验和可复用资产是什么
```

只有代码完成时，项目最多到第 5 或第 6 步。以后不能再把它称为完整闭环。

## 七、下一阶段的五条硬规则

1. **不理解业务目标和用户，不开始正式实现。**
2. **需求必须复述，完成标准、指标、ETA 和范围必须对齐。**
3. **风险在还能处理时暴露，不在延期后解释。**
4. **上线后按约定日期主动拿效果，没有效果也要给结论。**
5. **让 Leader 和协作者通过固定节奏知道进度，而不是等他们追问。**

再增加两条工程纪律：

6. **AI 生成的代码必须能逐行解释，并通过边界、数据口径和失败路径检查。**
7. **先判断慢在哪里，再决定补业务、数据、工程、沟通还是编码能力。**

## 八、下一份工作的前三十天

### 第 1 周：吸收上下文

- 画业务流程、系统调用、数据血缘和利益相关方四张图；
- 建立术语和数据字典；
- 跟随一次开发、测试、发布、监控和回滚；
- 主动约算法、后端、产品/运营和资深业务同学各一次交流；
- 每天下班前记录未知项，不让同一个关键问题悬空两天。

### 第 2 周：完成小闭环

- 独立完成一个范围清晰的小任务；
- 在开始前写一页 Problem、Goal、Metric、Plan、Risk、ETA；
- 中途至少主动同步一次；
- 交付后核对使用方是否真正拿到结果。

### 第 3 周：承担模块

- 自己给 Timeline 和里程碑；
- 建立风险和依赖清单；
- 对一个核心指标负责，而不是只对代码负责；
- 输出第一次面向非技术角色的 Demo。

### 第 4 周：主动获取反馈

与 Leader 做一次 1:1，直接询问：

- 当前表现与预期最大的差距是什么？
- 哪件事我应该更快、更主动？
- 下个月最希望我取得什么可量化结果？
- 我的汇报频率和粒度是否合适？

## 九、怎样判断自己真的改变了

不能只凭“我感觉更主动了”。至少观察以下证据：

| 能力 | 可观察证据 |
|---|---|
| 业务理解 | 两周内能无笔记讲清用户、流程、KPI、数据和上下游 |
| 沟通 | 重要回答前 30 秒先讲结论；周状态不需要 Leader 追问 |
| 结果意识 | 每个项目有模型/系统/采用/业务指标树和约定回看日期 |
| Ownership | Blocker 有 Owner、下一步和升级时间；依赖持续推进 |
| 工程适应 | 能独立走通本地开发、测试、发布、监控和回滚 |
| AI 验证 | 每次 AI 辅助提交都有边界用例、Diff 审查和结果验证 |

具体的 30/60/90 天动作和每周计分见[三个月能力改善计划](../study/05-三个月能力改善计划.md)。

## 十、最后给自己的判断

不需要用这一年的反馈证明自己“不适合互联网”或“不擅长工程”。这一年真正暴露的是：我过去建立了很强的个人技术解题模式，却没有同步建立业务组织中的结果交付模式。

这不是技术上限问题，也不是不可改变的性格问题，而是一组可以训练的行为：

- 更早提问；
- 更快对齐；
- 更短周期汇报；
- 更主动推动依赖；
- 更严格定义效果；
- 更及时复盘和展示结果。

下一份工作的目标不是证明自己从未犯过这些问题，而是用新的工作系统证明：相同的问题不会以相同方式再次发生。
