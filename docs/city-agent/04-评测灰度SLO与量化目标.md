# 城市异动诊断 Agent：评测、灰度、SLO 与量化目标

更新日期：2026-09-04

用途：定义城市异动诊断 Agent 从数据准备、离线评测到 Shadow、人工辅助、审批灰度和效果回看的统一验收体系。本文是下一阶段规划，不是已经上线的效果报告。

> **事实声明：城市异动诊断 Agent 当前没有可证明的诊断准确率、线上调用量、生产 QPS、生产延迟、建议采纳率或业务收益。本文出现的性能、准确率、样本量和收益数字，均明确标记为【规划门槛】或【预期目标】，不是现有实绩。已有阈值系统的离线评测数字也不能迁移为本 Agent 的效果。**

事实边界以[事实、指标与待补证台账](../evidence/01-事实指标与待补证台账.md)为准。本文是城市 Agent **正式评测 KPI、评测样本门槛、SLO、容量目标、发布 Go/No-Go 和业务效果数字的唯一权威来源**。其他文档可以给出访谈/工作分解预算、工具超时等实现示例和必须为零的安全不变量，但不得另行维护一套正式验收数字；发生冲突时以本文为准。

## 1. 状态标签与书写规则

后续所有评测报告、周报、面试材料和简历候选表述统一使用以下标签。

| 标签 | 含义 | 是否可以当作成果 |
|---|---|---|
| 【已证实事实】 | 有代码、脱敏材料或既有系统证据支持 | 只能在证据边界内表述 |
| 【待测基线】 | 当前现状未知，需要先采集的对照数据 | 不可以 |
| 【规划门槛】 | 进入下一阶段必须满足的 go/no-go 条件 | 不可以，达到并留证后才能转为实际结果 |
| 【预期目标】 | 希望项目带来的工程或业务改善 | 不可以 |
| 【实际结果】 | 已完成实验或灰度，并有样本、周期、对照和限制 | 当前城市诊断 Agent 暂无 |

### 1.1 当前状态

- 【已证实事实】人工阈值链路已有查询、配置预览、人工审批、确定性执行和审计底座；这些能力尚未被 Agent 直传入口完整串联。
- 【已证实事实】外部 Agent 接入当前只覆盖“接收结构化建议 → 有限字段校验 → 提交独立审批”，可以作为未来建议链路的起点。
- 【已证实事实】现有阈值系统有自己的结构化解析评测，但那是输入解析能力，不是城市异常诊断能力。
- 【待测基线】城市异常识别、多步诊断、证据绑定、运维指导、阈值建议和效果反馈目前均无正式结果。
- 【待测基线】诊断 Agent 的生产 QPS、延迟、可用性、成本和业务收益目前均无正式结果。

### 1.2 严禁混淆的口径

- 离线 Gold Set 通过率不等于线上准确率。
- Shadow 正确率不等于业务收益，因为 Shadow 不改变业务决策。
- 运营采纳率不等于建议正确率，采纳行为受人员、时效和风险偏好影响。
- 上线前后自然恢复不等于 Agent 带来的因果改善。
- 严格 JSON、工具调用成功和 Workflow 完成不等于诊断结论正确。
- 平均延迟不代表长尾体验，必须同时报告 P50、P95、P99 和超时率。
- 系统整体结果不能全部归因给 LLM；统计程序、数据质量、工具、规则、人工审批和执行底座都是系统组成部分。

## 2. 评测目标树

城市异动诊断 Agent 不能只优化一个“答案正确率”。完整目标分成六层。

```text
数据可信
  ↓
异常发现及时且少误报
  ↓
诊断范围、工具和证据正确
  ↓
根因与建议有用、可拒答
  ↓
执行安全、可恢复、可审计
  ↓
人工效率和业务结果得到受控改善
```

| 层级 | 核心问题 | 主要指标 |
|---|---|---|
| 数据层 | 输入能否相信 | 新鲜度、完整率、唯一性、Join 放大、单位与口径一致性 |
| 告警层 | 是否发现了真正异常 | Precision、严重异常 Recall、误报数、重复率、检测延迟 |
| 诊断层 | 是否找到正确范围、证据和根因 | Scope Exact Match、证据正确率、Top-K Recall、ABSTAIN |
| 建议层 | 是否应该调、怎样调才安全 | 行动判断、方向、允许区间、规则合法率、Dry Run 一致性 |
| 系统层 | 能否稳定运行和恢复 | 成功率、延迟、成本、并发、重试、Checkpoint、幂等 |
| 业务层 | 是否真正节省时间并改善结果 | MTTD、MTTA、人工分钟、异常持续时间、业务 Guardrail |

安全指标采用硬门槛，不能被平均准确率抵消。例如，很多普通案例答对不能抵消一次越权调整或一次重复写入。

## 3. 先采集 Baseline，再锁定目标

在开发 Agent 前，先完整记录现有人工流程。没有 Baseline，就无法证明“减少了多少时间”或“告警质量提高了多少”。

### 3.1 Baseline 采集周期

- 【规划门槛】连续采集最少 2 周、通常 2–4 周，并覆盖工作日、周末、高低峰和至少一次数据延迟或异常场景。
- 【规划门槛】同时满足时间门槛和预注册样本门槛后才能冻结 Baseline；若严重异常、关键根因或代表性 Scope 样本不足，即使满 4 周也应延长。
- 【规划门槛】每个流程阶段保留开始、结束、参与人、工具、结论和返工原因，不能只记录最终耗时。

### 3.2 统一事件时间点

所有 Baseline、Replay、Shadow、Pilot、Canary 和 Scale 报告统一记录以下时间点；缺失时写 `NULL + reason_code`，不得用相邻时间点悄悄代替。

| 时间点 | 统一定义 |
|---|---|
| `T_detectable` | 按冻结的检测规则和当时可见数据，异常首次满足“可被系统检测”条件的时间 |
| `T_alert` | 系统创建或合并 Episode 并发出首个有效告警的时间 |
| `T_ack` | 责任人首次确认接手该 Episode 的时间 |
| `T_evidence_ready` | 第一组通过口径、新鲜度和引用校验的证据就绪时间 |
| `T_recommendation` | 可供人工审核的结构化建议及其风险、观察窗、回滚条件就绪时间 |
| `T_product_review` | 产品审核对建议版本作出批准、编辑、拒绝或补证决定的时间；未展示则为空 |
| `T_downstream_approval` | 下游 BPM 对已绑定动作作出最终授权决定的时间；未提交则为空 |
| `T_execution_final` | 执行结果完成最终回查并进入可证明终态的时间；未执行则为空 |
| `T_recovery` | 预注册业务指标恢复到正常带并满足稳定窗口的时间 |

统一公式：

```text
MTTD = T_alert - T_detectable
MTTA = T_ack - T_alert
```

若历史数据无法还原 `T_detectable`，只能报告明确命名的代理指标及其推导方法，不能与标准 MTTD 合并比较。

### 3.3 待测 Baseline 指标

| 类别 | 【待测基线】字段 | 定义 |
|---|---|---|
| 告警 | 每城市日告警数、误报率、重复率 | 同一异常被多次提醒需要单独统计 |
| 发现 | MTTD | `T_alert - T_detectable` |
| 响应 | MTTA | `T_ack - T_alert` |
| 诊断 | 首条可信证据时间、根因确认时间 | 分开记录“有迹象”和“确认根因” |
| 决策 | 可审核建议时间、审批提交时间 | 不把口头讨论算成已形成方案 |
| 人力 | 人工分钟、查询次数、沟通轮次 | 每个 Episode 聚合 |
| 质量 | 复查修改、误判、漏判、升级、回滚 | 需要原因分类 |
| 执行 | 产品审核耗时、下游审批耗时、执行成功、最终回查一致 | 任一审批通过都不等于配置已生效 |
| 业务 | 异常持续时间、目标 KPI 恢复时间 | 同时记录天气、活动和其他操作 |
| 工程 | 请求量、峰值、延迟、失败率、成本 | 当前均不能从设计稿推断 |

### 3.4 Baseline 冻结要求

- 写明统计周期、城市或区域范围、分母、缺失样本和异常剔除规则。
- 报告中位数、P90、P95，而不是只报平均值。
- 分严重度、城市规模、根因和时段切片，避免大城市或高频类型掩盖问题。
- 保存一份不可变 Baseline 版本；目标可以调整，但不能事后改基线来制造提升。

## 4. Episode 数据契约

### 4.1 一条样本的时间轴

```text
异常开始（可能未知）          告警/请求 T0                  观察窗结束
       |--------------------------|-----------------------------|
                         Agent 只能看 T0 及以前         T0 以后只作结果标签
```

一条 `anomaly_episode` 是评测的最小单位。`feature_cutoff = decision_cutoff = T0`。进入 Agent 输入的数据必须同时满足：

```text
event_time <= feature_cutoff
available_at <= decision_cutoff
ingested_at <= decision_cutoff
```

`event_time` 表示业务事件发生，`available_at` 表示来源系统当时已可查询，`ingested_at` 表示本系统当时已实际摄取。T0 后发生或 T0 后才可获得的数据只能用于结果标签与效果回看，不能回填诊断输入。`allowed_lateness` 只用于标记数据质量、补算和监控水位，不得突破 Point-in-Time 截止线。

### 4.2 建议的数据实体

| 实体 | 关键字段 | 目的 |
|---|---|---|
| Episode | `episode_id`、触发时间、触发源、严重度、脱敏 scope、检测器版本 | 定义一件异常事件 |
| Metric Snapshot | 数据时间、口径版本、指标值、分子分母、滚动基线、缺失状态 | 固化 T0 时可见事实 |
| Evidence | `evidence_id`、工具、参数摘要、事件/可用/摄取时间、口径版本、结果摘要和内容 hash | 保存不可变事实，不在事实对象里预先写结论 |
| Hypothesis | `hypothesis_id`、候选根因、版本、状态和置信依据 | 保存待证实或待反驳的解释 |
| Evidence-Hypothesis Relation | `relation_id`、`evidence_id`、`hypothesis_id`、`SUPPORTS/REFUTES/NEUTRAL`、强度和判定来源 | 将事实与解释的关系独立版本化和审计 |
| Expert Label | 是否异常、影响范围、根因、关键证据、是否行动、允许动作 | 提供评测真值或允许集合 |
| Recommendation | 建议版本、动作、方向、允许区间内候选值、风险、观察与回滚 | 评测建议质量 |
| Decision & Execution | 查看、修改、拒绝、BPM、配置版本、执行和最终回查 | 还原人机决策链 |
| Outcome | 预定义观察窗、业务指标、控制组、同期其他操作 | 评估实际效果 |

### 4.3 数据源分层

可规划为以下受控、只读和聚合后的数据域：

- 需求侧：订单、请求、取消和履约；
- 供给侧：可用车辆、低电车辆、区域分布和供需缺口；
- 能力侧：换电量、等待、站点或运营能力；
- 过程侧：工单创建、积压、完成和超时；
- 策略侧：当前阈值、合并后配置、变更历史、在途审批和冷却期；
- 环境侧：天气、节假日、公开活动等可授权数据；
- 稳定性侧：服务错误、数据延迟、任务堆积和已有告警；
- 质量侧：分区状态、重复、缺失、冲突和指标口径版本。

模型不得提交任意 SQL。工具层负责身份、scope、时间跨度、返回行数、超时、脱敏和审计。外部数据缺失时输出 `UNKNOWN`，不得由模型补猜。

### 4.4 数据质量断言

- `episode_id` 唯一；同一告警聚合规则固定。
- 所有输入事实同时满足 `event_time <= feature_cutoff`、`available_at <= decision_cutoff` 和 `ingested_at <= decision_cutoff`。
- `allowed_lateness` 只影响数据质量状态、补算队列与告警，不允许把截止线之后才可见的数据用于当时决策。
- Join 前后检查行数、业务键唯一性和一对多放大。
- 所有比例保存 numerator、denominator 和 rate。
- 所有时长保存单位；缺失与真实零分开。
- 分区到达时间和数据新鲜度可查询。
- 配置快照保存版本，建议审批时必须重新验证版本。
- 工具响应保存版本、摘要和 hash，使历史 Replay 可重现。

## 5. 标签体系

### 5.1 异常标签

- 是否真实异常：`TRUE / FALSE / UNCERTAIN`；
- 影响范围：城市、区域、车型、时段及组合；
- 严重度：由业务规则确定，不让 LLM 自由生成；
- 异常开始、发现和恢复时刻；
- 数据质量是否足以判断。

### 5.2 分层多标签根因

根因不强制单选。建议初始 taxonomy：

- `DATA_QUALITY`：数据缺失、延迟、重复或口径漂移；
- `DEMAND_SURGE`：需求短时或持续增加；
- `VEHICLE_SUPPLY_SHORTAGE`：有效供给不足或分布不均；
- `LOW_BATTERY_ACCUMULATION`：低电车辆聚集；
- `SWAP_CAPACITY`：换电能力或处理能力受限；
- `WORK_ORDER_BACKLOG`：工单创建、流转或完成异常；
- `DISPATCH_OR_POLICY`：调度或既有策略造成偏差；
- `THRESHOLD_MISMATCH`：当前阈值与环境不匹配；
- `WEATHER_OR_EVENT`：天气、节假日或活动背景；
- `UPSTREAM_SYSTEM`：依赖服务或上游链路异常；
- `MULTI_CAUSE`：多个原因共同作用；
- `OTHER`：已有证据，但当前 taxonomy 尚未覆盖；
- `UNKNOWN`：证据不足、冲突或无法确认。

每个根因都要标 `primary/supporting`、支持证据、反驳证据和置信等级。置信等级由数据完整度、证据一致性和基线稳定性计算，不直接使用模型自报概率。

### 5.3 决策与动作标签

```text
NO_ANOMALY
MONITOR
MANUAL_INVESTIGATION
OPS_GUIDANCE
THRESHOLD_CHANGE
ROLLBACK
ESCALATE
ABSTAIN
```

阈值动作标签不要求一个唯一精确数值，而应保存：

- 是否允许调整；
- 作用 scope；
- 调整方向；
- 合法候选区间；
- 禁止组合和风险等级；
- 冷却期、观察窗和回滚条件。

### 5.4 反馈标签的边界

- 运营采纳、修改和拒绝是偏好与流程反馈，不自动视为正确答案。
- 只有被执行的建议才有后验结果，会产生选择偏差。
- “异常自然恢复”可能来自均值回归、天气、供给或其他人工操作。
- 训练和评测必须保留未采纳建议、无异常阴性样本和 ABSTAIN 样本。

## 6. Gold Set、安全集与数据切分

### 6.1 初始 Gold Set

- 【规划门槛】MVP 至少建立 300 个历史 Episode。
- 【规划门槛】覆盖不同城市规模、时段、严重度、根因、可行动和不可行动案例。
- 【规划门槛】必须包含安静时段和误报告警阴性样本，不能只从已有告警中选正例。
- 【规划门槛】至少 20% 样本由两名标注者独立标注并经资深人员仲裁。
- 【规划门槛】多标签根因一致性不能只报一个总体 Kappa：逐标签按标注人数报告 Cohen/Fleiss κ，或在缺失、类别不均衡等场景使用 Krippendorff's alpha；同时报告样本类别分布、Jaccard、micro/macro-F1 及 95% 置信区间。首版可把逐标签一致性 0.75、是否行动一致性 0.80 作为【项目预算假设】，最终阈值由标注试运行、类别分布和置信区间冻结；未达到时先修标注规范。

### 6.2 建议切分

- 【规划门槛】约 60% 用于 Workflow、Prompt 和规则开发；约 20% 作为固定回归锚点；约 20% 作为按时间向后的盲测集。
- 【规划门槛】同一 Episode 的不同轮次、相邻重复告警和同源派生样本不能跨集合。
- 【规划门槛】另设跨城市、跨时段或新根因 OOD Challenge Set，不用普通随机切分代替。
- 【规划门槛】盲测集在版本决策前不可用于 Prompt 调试。

### 6.3 安全与对抗集

- 【规划门槛】初始至少 100 条，后续每个生产 Badcase 都追加回归用例。
- 数据过期、分母为零、指标冲突、缺失关键分区；
- 伪造实体、越权 scope、超大时间范围、超大批量；
- Prompt Injection、工具返回中的恶意文本和指令覆盖；
- 配置版本变化、在途审批、冷却期、重复回调；
- 工具超时、部分成功、响应损坏、LLM 超时；
- 执行状态未知、网络重试和进程重启；
- 极端但合法的业务值，以及“有证据但不该调整”的案例。

确定性故障注入和合成样本可补充安全测试，但不得与真实 Episode 混在一起计算业务诊断准确率。

### 6.4 滚动维护

- 【规划门槛】上线后每周分层抽样约 50 条，具体数量按真实流量调整。
- 全部严重告警、运营修改/拒绝、异常执行、回滚和高置信错误进入 Badcase 池。
- 固定锚点集长期保留；滚动集按时间更新，用于发现数据和行为漂移。
- 数据、标签规范、模型、Prompt、工具 Schema 和 Workflow 都必须版本化。

### 6.5 统计判定与证据不足状态

任何 Precision、Recall、准确率、完成率、采纳率和错误率都必须同时报告分子、分母、点估计和 95% 置信区间；比例指标默认使用 Wilson 区间，极低频安全事件可使用 Clopper-Pearson 精确区间。版本冻结前应按预期基线、最小可接受差异、显著性和检验功效重新做 Power Analysis，下列仅是首版门槛。

- 【规划门槛】用于整体主要质量指标判定的独立 Episode 分母不少于 100。
- 【规划门槛】Replay 与 Shadow 的严重异常切片各不少于 30 条；若 Power Analysis 给出更大样本，以更大值为准。
- 【规划门槛】每个需要作 Go/No-Go 结论的关键根因或重点 Scope 切片不少于 30 条；不足时只能列观察值。
- 【规划门槛】Shadow 除总量门槛外还必须满足严重样本门槛，不能用大量普通样本稀释高风险样本不足。
- 【规划门槛】任一必需分母、切片或观察窗口不足时，状态写作 `INSUFFICIENT_EVIDENCE`，不能标记 Go，也不能把“未观察到错误”写成“已证明安全”。
- 【规划门槛】对零安全事故同时报告 `0/n` 和置信区间上界；`0` 次观测事故只满足当期硬停止检查，不等于真实风险为零。

阈值比较在实验前预注册：质量收益指标优先检查置信区间下界或非劣界，安全指标按事件计数硬停止。不得在看完结果后更换区间算法、切片或最小样本量。

## 7. 离线评测体系

### 7.0 Agent Eval 的统一对象

评测对象采用 [Anthropic《Demystifying evals for AI agents》（2026-01-09）](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 中可复用的基本拆分，并映射到本项目：

| 对象 | 本项目定义 |
|---|---|
| Task | 一条有初始状态、可用工具、预算和成功标准的 Episode |
| Trial | 固定 Task、版本和随机种子策略下的一次独立运行 |
| Grader | 对结果或轨迹评分的确定性程序、模型评审器或领域专家 |
| Transcript / Trace | 节点、工具参数与返回、证据引用、状态迁移、成本和时间的完整轨迹 |
| Outcome | 外部可验证的最终状态，例如证据是否真实、建议是否合法、执行终态是否一致；不是 Agent 自称成功 |
| Eval Harness | 构造环境、执行 Trial、故障注入、采集 Trace 和汇总统计的评测框架 |

- 【规划门槛】对含模型采样或非确定工具行为的关键 Task 运行多次 Trial，并报告均值、方差、最差结果和失败模式；安全硬错误任一次出现即 No-Go。
- 【规划门槛】组合使用程序 Grader、模型 Grader 和专家盲审：数值、Schema、权限、幂等与终态用确定性程序；解释质量可由模型预评，但必须用专家样本校准。
- 【规划门槛】维护两类套件：Capability Suite 检查当前能力上限，Regression Suite 固定历史 Badcase 防止已解决问题回归。
- 【规划门槛】评测从开发首周建立，包含正例、阴性、ABSTAIN、数据故障和攻击样本；不等到上线前才补测试。
- 【规划门槛】Outcome 与必要轨迹同时评分，但不把某一条固定工具调用顺序当作唯一正确答案；人工抽查必须阅读原始 Trace。

上述来源用于定义评测方法，不把任何供应商或其他 Agent 的公开结果外推为本项目指标。

### 7.1 数据与异常检测层

#### 指标

- 数据新鲜度通过率、分区完整率、重复率、Join 放大率；
- Episode Precision、Recall、F1；
- 严重异常 Recall；
- 每城市日误报告警数；
- 重复告警率；
- 检测延迟 P50、P95；
- 按城市规模、时段、严重度和异常类型的切片表现。

Episode 匹配必须预先定义：相同或可包含的 scope、同一异常类型，以及相对数据刷新周期确定的时间容忍窗。

#### 初始门槛

- 【规划门槛】严重异常 Recall 不低于 90%。
- 【规划门槛】整体 Precision 不低于 75%。
- 【规划门槛】误报告警不高于 0.2 次/城市日。
- 【规划门槛】重复告警率不高于 5%。
- 【规划门槛】P95 检测延迟不超过 2 个数据刷新周期。

以上是初始建议值，Baseline 完成后允许前置评审调整，但不能在看到最终实验结果后修改。

### 7.2 Scope 与工具调用层

#### 指标

- 城市、区域、车型、时段 Scope Exact Match；
- 工具选择 Accuracy、macro-F1；
- 参数字段级准确率、Schema 通过率和实体归属合法率；
- 无效调用、重复调用、无增量证据调用；
- 工具超时后的恢复或正确终止；
- 工具预算内完成率。

#### 初始门槛

- 【规划门槛】Scope Exact Match 不低于 95%。
- 【规划门槛】工具参数 Schema 通过率不低于 99%。
- 【规划门槛】越权工具调用阻断率为 100%。
- 【规划门槛】同参数重复调用率不高于 2%。
- 【规划门槛】达到预算上限后终止或降级率为 100%，不能无限循环。

### 7.3 证据与 Grounding 层

#### 指标

- Evidence Precision：引用证据中真正支持结论的比例；
- Evidence Recall：专家关键证据被覆盖的比例；
- Citation Correctness：`evidence_id` 是否真实存在且对应正确工具结果；
- Numeric Traceability：每个数值是否可追到数据时间、口径、分子分母；
- Unsupported Claim Rate：没有任何证据支持的事实声明比例；
- Contradiction Check Recall：是否发现反驳主要假设的证据。

#### 初始门槛

- 【规划门槛】关键数值可追溯率为 100%。
- 【规划门槛】Evidence Precision 不低于 95%。
- 【规划门槛】Citation Correctness 不低于 98%。
- 【规划门槛】关键证据 Recall 不低于 90%。
- 【规划门槛】Critical Unsupported Claim 为 0。

### 7.4 根因诊断层

#### 指标

- 多标签 micro/macro-F1；
- Primary Cause Top-1 Recall；
- 候选原因 Top-3 Recall；
- 根因排序 nDCG；
- 严重案例 Recall；
- 证据冲突时的降置信或 ABSTAIN；
- 校准指标：Brier Score、ECE、Risk-Coverage Curve。

真实根因经常多因共存，因此 Top-K、multi-label 和证据链比强制 Exact Match 更合理。

#### 初始门槛

- 【规划门槛】Top-3 根因 Recall 不低于 85%。
- 【规划门槛】Top-1 根因 Recall 不低于 65%。
- 【规划门槛】证据不足案例的 ABSTAIN Recall 不低于 90%。
- 【规划门槛】可解案例的过度拒答率不高于 30%。
- 【规划门槛】高置信 Critical 错误为 0。

### 7.5 建议质量层

#### 指标

- `应调整 / 不调整 / 继续观察 / 转人工` macro-F1；
- 调整方向准确率；
- 建议数值命中专家允许区间率；
- Scope 完整率和多目标覆盖率；
- 风险、观察窗和回滚条件完整率；
- 运营盲评的有帮助率；
- 无修改采纳、修改后采纳、拒绝和拒绝原因；
- ABSTAIN 是否在正确时机发生。

#### 初始门槛

- 【规划门槛】是否行动 macro-F1 不低于 85%。
- 【规划门槛】调整方向准确率不低于 90%。
- 【规划门槛】合法区间命中率为 100%。
- 【规划门槛】Scope 完整率为 100%。
- 【规划门槛】专家盲评“有帮助”比例不低于 70%。
- 【规划门槛】Critical Unsafe Suggestion 为 0。

“有帮助率”和“采纳率”是实用性信号，不取代安全与诊断正确性指标。

### 7.6 执行安全层

#### 指标与门槛

- 【规划门槛】Java/规则引擎合法率为 100%。
- 【规划门槛】越权、跨 Scope 和禁用动作阻断率为 100%。
- 【规划门槛】Dry Run Diff 与最终提交内容一致率为 100%。
- 【规划门槛】配置版本冲突阻断率为 100%。
- 【规划门槛】在途审批和冷却期检查覆盖率为 100%。
- 【规划门槛】重复 BPM、重复执行和无审计写入均为 0。
- 【规划门槛】审批回调后最终状态可查询率为 100%。
- 【规划门槛】回滚演练成功率为 100%。

上述安全项按单项判定，不能报告一个模糊的“安全准确率”。

### 7.7 轨迹与 Workflow 层

#### 指标

- 节点级成功率与错误类型；
- 平均、P95 和最大节点数；
- 平均工具数、模型调用数和 Token；
- 重复路径、路径震荡和最大步数触发率；
- 新证据带来的不确定性下降；
- Checkpoint 恢复、人工中断恢复和幂等重放；
- 同一输入多次运行的决策一致率；
- 模型、Prompt、工具和 Schema 版本可重现率。

#### 初始门槛

- 【规划门槛】Workflow 完成率不低于 99%。
- 【规划门槛】相同输入的最终决策一致率不低于 95%，允许措辞变化。
- 【规划门槛】所有终止都能解释为完成、ABSTAIN、人工升级或预算超限，不存在未知死循环。
- 【规划门槛】故障注入后的 Checkpoint 恢复成功率为 100%。
- 【规划门槛】关键 Trace 字段完整率不低于 99.9%。

### 7.8 端到端与鲁棒性

端到端分数至少包括：

- 最终决策准确率；
- 事实—假设—建议引用链完整率；
- 严重异常漏报与错误行动数；
- 按城市、根因、严重度、时间和数据缺失切片；
- Prompt 扰动、工具返回顺序变化和模型采样扰动；
- OOD 城市、未见根因和数据分布漂移；
- P50/P95/P99、超时、错误和单次成功成本。

可使用非对称损失：严重异常漏报、越权或错误执行的代价远高于普通误报。LLM-as-Judge 只能辅助评价表达清晰度和运维指导可用性；事实、数值、安全和执行一致性必须由确定性程序或盲审专家判定。

## 8. 微调模型的触发条件与评测

### 8.1 默认策略

初期不微调。优先依靠：

- 确定性异常检测和统计计算；
- 结构化输出与严格 Schema；
- 状态化 Workflow 和有界工具循环；
- 证据检索、上下文裁剪和规则护栏；
- 大小模型路由与失败降级。

数值计算、权限、合法区间和执行安全不能通过“训进模型”替代程序。

### 8.2 何时才考虑 SFT

- 下述样本数是【项目预算假设】，用于预估标注和训练成本，不是通用经验阈值。是否启动微调最终由学习曲线、95% 置信区间、关键切片覆盖、错误类型饱和度和预注册 Power Analysis 共同决定。
- 【规划门槛】【项目预算假设】积累至少 1,000 条已仲裁的 Episode 或 Tool Trace。
- 【规划门槛】Badcase 证明错误稳定集中在意图、Scope、工具计划或结构化摘要，而不是数据缺失或规则缺陷。
- 【预期目标】【项目预算假设】积累 2,000–5,000 条高质量样本后，再评估是否值得训练小模型路由器或结构化生成器。

不训练隐式思维链，不把运营采纳直接当金标，不让微调模型独立决定高风险数值。

### 8.3 微调 go/no-go

- 以下提升幅度同样是【项目预算假设】；正式 Go/No-Go 使用置信区间、关键切片非劣性、错误饱和和功效分析冻结，不因训练结果“接近目标”而事后放宽。
- 【规划门槛】【项目预算假设】盲测工具与参数 Exact Match 相对基础方案提升至少 5 个百分点。
- 【规划门槛】端到端诊断质量不下降，Critical Safety Error 保持为 0。
- 【规划门槛】跨城市和按时间向后的 OOD 集不退化。
- 【预期目标】【项目预算假设】相较大模型方案，P95 延迟或单次成本至少下降 30%。

若只提升格式而损害诊断、证据或拒答能力，则 no-go。

## 9. 分阶段上线与 Go/No-Go

### 9.1 Replay：历史冻结回放

范围：使用冻结快照回放，不访问生产写工具。

- 【规划门槛】完成至少 300 个 Gold Episode 和至少 100 个安全/对抗案例。
- 【规划门槛】所有工具响应可重放，版本和数据时间可追踪。
- 【规划门槛】达到数据、诊断、建议和安全的离线门槛。
- 【规划门槛】越权、伪造证据、重复副作用和无限循环均为 0。

No-Go：任一 Critical Safety Error；关键数值不可追溯；盲测集明显退化；数据快照无法复现。

### 9.2 Shadow：线上只读影子运行

范围：接入真实触发和只读工具，但结果不展示给运营、不发起 BPM、不改变配置。

- 【规划门槛】最少运行 2 周，累计不少于 500 个 Episode，并满足不少于 30 条严重异常的切片门槛；任一条件不足都继续延长，通常按 2–4 周规划。
- 【规划门槛】至少抽取 200 条做人工盲审。
- 【规划门槛】覆盖代表性 Scope、高低峰和数据迟到场景。
- 【规划门槛】数据质量检查覆盖率为 100%，Trace 完整率不低于 99%。
- 【规划门槛】Workflow 完成率不低于 99%，Critical 幻觉、越权和写操作为 0。
- 【规划门槛】严重异常 Recall、证据正确性和 P95 延迟达到既定门槛。

Shadow 只能证明真实环境下的可运行性和诊断一致性，不能证明业务收益。

### 9.3 Pilot：人工辅助试点

范围：向运营展示异常事实、证据、运维指导和阈值 Dry Run，但禁止提交 BPM。

- 【规划门槛】选择 5–10 个有代表性的 Scope。
- 【规划门槛】运行至少 2 周，积累至少 100 条人工审核建议。
- 【规划门槛】记录查看、采用、修改、拒绝、耗时和原因。
- 【规划门槛】用滚动 7 日和 14 日窗口计算可用性、失败率、延迟和质量错误预算；任一核心预算耗尽即暂停扩量并回到上一模式。
- 【规划门槛】Pilot 未连续覆盖完整自然月前，只报告滚动窗口结果，不宣称达到月度 SLO。
- 【规划门槛】Critical Unsafe Suggestion 为 0，Evidence-less Claim 为 0。
- 【规划门槛】专家有帮助率不低于 70%。
- 【预期目标】人工诊断耗时相较冻结 Baseline 下降至少 30%。
- 【预期目标】无修改采纳率达到 60%，但该指标不作为唯一安全门槛。

No-Go：运营必须频繁重做 Scope 或查询；告警噪声明显增加；高置信错误出现；工具或解释不可追溯。

### 9.4 Canary：审批执行小流量验证

范围：Agent 可生成结构化建议，但必须先经产品审核，再由应用侧可靠提交既有下游 BPM；不开放自主生产写入。

仅允许：低风险、单 Scope、单变量、规则区间内、无在途审批、配置版本一致、通过冷却期的建议。

- 【规划门槛】从不超过 5% 的 eligible Episode 或少数试点 Scope 开始。
- 【规划门槛】设置每天最大建议提交量和一键 Kill Switch。
- 【规划门槛】至少完成 30 次真实审批/执行，并观察完预注册效果窗口；这是早期“零事故”闸门，不足以证明 99.5% 的长期终态 SLO。
- 【规划门槛】上述早期样本内，执行终态未知、重复 BPM、重复写入、越权和无审计执行均为 0；同时报告 `0/n` 的置信区间上界。
- 【规划门槛】配置版本冲突阻断率和回滚演练成功率均为 100%。
- 【规划门槛】所有业务 Guardrail 无超过非劣界的恶化。

只有累计样本量达到预注册 Power Analysis 要求，且跨越足够业务周期后，才能判断长期“下游批准至最终状态可证率 ≥99.5%”这一【规划门槛】；否则状态为 `INSUFFICIENT_EVIDENCE`。

### 9.5 Scale：逐级扩量

- 【规划门槛】按 5% → 25% → 50% → 更广覆盖逐级推进。
- 【规划门槛】每档至少跨越一个完整业务周期并达到最小有效样本量。
- 【规划门槛】高风险动作永久保留人工审批；“全量覆盖”也不等于自动写生产。
- 【规划门槛】每档使用独立版本、效果报告和回滚点。

### 9.6 全阶段硬停止条件

发生任一项立即停止扩量并降级到 read-only：

- 任一次越权、跨 Scope、重复执行或无审计写入；
- 任何敏感信息泄露或 Prompt Injection 逃逸到高风险工具；
- 配置版本冲突未被阻断；
- 关键数据过期仍生成调整建议；
- 回滚失败或执行状态无法最终确认；
- Critical Guardrail 越过预设边界；
- 连续两个监控窗口违反核心 SLO；
- 高置信错误或运营修改/拒绝率出现显著异常漂移。

## 10. 因果实验与业务效果

### 10.1 推荐实验设计

若条件允许，对 eligible Episode 按城市规模、严重度和根因分层，随机进入：

- Control：现有人工流程；
- Treatment：Agent 辅助诊断与建议，仍需产品审核与下游 BPM 授权。

按 Intent-to-Treat 分析，不能只挑最终使用了建议的样本。若无法随机，可采用：

- 阶梯式 Rollout；
- 城市或时段 Switchback；
- 匹配控制城市；
- Difference-in-Differences，并检查 pre-trend。

如果同一城市内策略会互相影响，应提升随机化单位，避免控制组受到处理组阈值变化污染。

### 10.2 实验前注册

- Primary Metric；
- Guardrail Metrics；
- 样本单位和随机化单位；
- 效果观察窗；
- 并发运营动作、天气、活动和数据异常的处理规则；
- 最小样本量和 Power Analysis；
- 中途停止和回滚条件；
- 多重比较校正方法。

正式报告至少给出样本量、绝对值、相对变化、95% 置信区间和失败案例，不能只给一个百分比。

### 10.3 过程指标

| 指标 | 定义 |
|---|---|
| MTTD | `T_alert - T_detectable` |
| MTTA | `T_ack - T_alert` |
| Time to First Evidence | `T_evidence_ready - T_alert` |
| Time to Reviewed Recommendation | `T_recommendation - T_alert` |
| Manual Minutes per Episode | 每条 Episode 实际人工投入 |
| Investigation Steps | 查询、沟通和工具切换次数 |
| Escalation Rate | 需要升级给专家或其他团队的比例 |

### 10.4 质量指标

- 专家诊断一致率；
- 有帮助率；
- 无修改采纳、修改后采纳和拒绝；
- 修改字段、修改幅度和拒绝原因；
- ABSTAIN 后人工确认“确实不应自动建议”的比例；
- 误建议、回滚和高置信错误。

### 10.5 业务结果指标

最终只选择一个与业务确认的 Primary，其他作为 Secondary 或 Guardrail：

- 异常持续时间；
- 目标 KPI 恢复到正常带所需时间；
- 异常偏离曲线面积 AUC；
- 低电车辆积累、工单积压或供需缺口；
- 履约、取消、车辆可用性或换电处理能力；
- 策略调整后的反向副作用。

不同根因需要不同 Primary。数据质量故障的成功标准可能是停止错误建议并通知修复，而不是阈值调整。

### 10.6 Guardrail

- 服务成功或履约不恶化；
- 取消、投诉和异常操作不增加；
- 阈值波动次数和幅度不过度；
- 运营告警负担不增加；
- 审批、执行和回滚风险不增加；
- 成本不突破预算。

## 11. SLI、SLO、容量与成本

以下均为初始工程目标，正式值要在 Baseline 和压测后冻结。Pilot 只按滚动 7 日/14 日窗口消耗错误预算；连续覆盖一个完整自然月后，才可以讨论“月 SLO”，且必须保留当月分母和中断明细。

### 11.1 可用性与响应

| SLI | 【规划门槛】Pilot 滚动 7 日/14 日 | 【预期目标】完整月稳定阶段 |
|---|---:|---:|
| 服务可用性 | ≥99.5% | 月度 ≥99.9% |
| 创建 Workflow ACK P95 | ≤500ms | ≤500ms |
| 正常队列等待 P95 | ≤5s | ≤5s |
| 告警风暴队列等待 P95 | ≤30s | ≤30s |
| 首条确定性证据 P95 | ≤10s | ≤10s |
| 标准诊断 P50 | ≤30s | ≤30s |
| 标准诊断 P95 | ≤90s | ≤90s |
| 标准诊断 P99 | ≤180s | ≤180s |
| 深度诊断硬截止 | ≤5min | ≤5min |
| 关键只读工具成功率 | ≥99.5% | ≥99.9% |
| 关键只读工具 P95 | ≤3s | ≤3s |
| Workflow 完成率 | ≥99% | ≥99.5% |

深度诊断采用异步模式。超时后返回已经验证的事实、缺失证据和 ABSTAIN，不为追求完整答案突破预算。

错误预算按真实请求或分钟分母计算：`预算 = 分母 × (1 - SLO)`。Pilot 同时查看 7 日与 14 日 burn rate；任一窗口耗尽即停止扩量。低流量窗口达不到第 6.5 节最小样本时标记 `INSUFFICIENT_EVIDENCE`，但 Critical 事件仍立即触发硬停止。

### 11.2 状态恢复

- 【规划门槛】由编排器按节点或 super-step 边界自动持久化 Checkpoint；节点应围绕可恢复边界拆分，不能依赖业务代码“记得手工存一次”。
- 【规划门槛】进程重启和人工暂停恢复演练成功率为 100%。
- 【规划门槛】已审批副作用不丢失、不重复。
- 【预期目标】故障恢复 RTO 不超过 15 分钟。
- 【规划门槛】恢复时重新检查配置版本、在途审批、数据新鲜度和幂等状态。
- 【规划门槛】长期“下游批准至最终状态可证率 ≥99.5%”仅在累计样本满足 Power Analysis 后判定；Canary 前 30 次 `0` 事故仅是早期放行闸门。

### 11.3 容量和 QPS

下列是压测场景，不代表已有生产流量或覆盖范围。

- 【规划门槛】入口持续接收并成功入队至少 1 个标准 Workflow/秒，突发至少 5 个/秒；该值只表示 admission rate。
- 【规划门槛】同时在途 Workflow 至少 50 个。
- 【规划门槛】工具网关持续至少 20 QPS、突发至少 50 QPS。
- 【规划门槛】稳态完成吞吐不少于 0.8 个显式终态 Workflow/秒，完成、ABSTAIN、升级和预算终止均需可区分，未知状态不计完成。
- 【规划门槛】300 个 Scope 的巡检或诊断任务中，至少 95% 在 10 分钟内进入显式终态，剩余任务在 15 分钟内终止或转人工；不能只统计“已经启动”。
- 【规划门槛】压测同时报告 admission rate、completed workflows/s、在途数和 oldest queue age；突发结束后 10 分钟内，oldest queue age 应恢复到 5 秒以下。
- 【规划门槛】正式容量取 `max(观测 P95 峰值的 2 倍, 预定义告警风暴负载)`。
- 【预期目标】水平扩容效率不低于 70%，直到数据源或模型服务成为明确瓶颈。

### 11.4 调用与 Token 预算

| 类型 | 【规划门槛】模型调用 | 【规划门槛】工具调用 | 【规划门槛】Token P95 |
|---|---:|---:|---:|
| 标准诊断 | ≤3 | ≤8 | 输入≤30k，输出≤3k |
| 深度诊断 | ≤6 | ≤20 | 输入≤80k，输出≤8k |

超过预算后必须 early stop、切换便宜模型、返回部分事实或 ABSTAIN，不能无限扩展 Context。

### 11.5 成本

- 单次成功诊断成本同时包含模型、工具查询、计算和存储。
- 价格表保存供应商、模型版本、币种和生效日期；不在长期文档写死易过期单价。
- 成本分布报告 P50/P95/P99，并单独报告失败请求和重试浪费。
- 【预期目标】相较顺序执行的 B0，通过并行独立工具、预聚合、缓存、Context 裁剪和大小模型路由，使吞吐达到至少 3 倍、完整诊断 P95 降低至少 40%、平均单次成本降低至少 30%。
- 【规划门槛】上述优化后端到端质量下降小于 1 个百分点，Critical Safety Error 仍为 0；压测完成前不得写成“QPS 提升”或“延迟下降”的实绩。

## 12. 线上监控、告警与自动降级

### 12.1 系统运行模式

```text
SHADOW
READ_ONLY
ADVISORY
APPROVAL_ENABLED
```

故障时只能向更低权限模式降级，不能自动向高权限模式恢复。恢复 `APPROVAL_ENABLED` 必须由人工确认。

### 12.2 INC-P0：立即停用建议/执行

- 任一次越权、重复执行、无审计写入或敏感数据泄露；
- Prompt Injection 影响到高风险工具；
- 配置版本冲突未阻断；
- 回滚失败或最终执行状态不可确认；
- Critical Guardrail 越界。

动作：立即切至 `READ_ONLY`，启用 Kill Switch，冻结证据和 Trace，通知负责人并启动复盘。

### 12.3 INC-P1：自动降级并通知

下表所有数字均为【规划门槛】。告警规则必须同时配置统计窗、最小样本、Owner 和恢复判据；低流量不足最小样本时进入 `INSUFFICIENT_EVIDENCE`，同时启用表内事件型兜底，不能因为样本少而忽略严重故障。

| 信号 | 触发窗口与最小样本 | Owner | 恢复判据 |
|---|---|---|---|
| 关键数据新鲜度 | 每个计划刷新周期检查，至少 1 个应到分区；超过该源 SLA 立即触发 | 数据 Owner | 连续 2 个刷新周期按时且完整 |
| Workflow 失败率 | 滚动 15 分钟、至少 50 个终态 Workflow，失败率 >2%；样本不足时连续 3 次失败或任一严重 Episode 失败即触发 | Workflow Owner | 连续 2 个完整窗口失败率 ≤1% |
| 端到端 P95 | 滚动 15 分钟、至少 50 个终态 Workflow，连续 2 个窗口超过第 11.1 节 SLO | Workflow 与模型 Owner | 连续 2 个完整窗口回到 SLO 内 |
| Oldest queue age | >60 秒持续 5 分钟，无样本门槛 | Workflow Owner | <5 秒持续 10 分钟，且无未知终态 |
| 关键工具健康 | 任一请求出现权限、Schema 或确定性数据错误即触发；普通失败按滚动 15 分钟至少 50 次调用评估 | 工具 Owner | 连续 2 个完整窗口成功且 Schema 校验通过 |
| Citation Correctness | 滚动 24 小时、至少 50 条人工或程序审计输出，低于 98% | Eval Owner | 最近 50 条 ≥98%，且 Critical Unsupported Claim 为 0 |

动作：停止生成阈值建议，只返回确定性事实、缺失数据和恢复预估。

### 12.4 INC-P2：日/周治理

- 【规划门槛】按自然日统计成本，超过当日预算的 1.5 倍；Owner 为平台负责人，连续 2 日回到预算内后关闭。
- 【规划门槛】滚动 7 日、至少 30 条人工审核中，编辑/拒绝率相对冻结 Baseline 超过预注册漂移界；Owner 为产品与 Eval 负责人，最近 30 条恢复且 Badcase 复核完成后关闭。
- 【规划门槛】滚动 7 日且关键切片至少 30 条时，某城市、根因或时段表现连续退化；Owner 为 Eval 与对应业务负责人，修复版本通过固定回归集后关闭。
- 【规划门槛】滚动 24 小时检查重复调用、过度 ABSTAIN 和 Context 预算；Owner 为 Workflow Owner，连续 2 个窗口恢复后关闭。
- 【规划门槛】每个数据刷新周期检查分布、缺失率和工具错误漂移；Owner 为数据与工具负责人，连续 2 个周期恢复并完成影响回看后关闭。

动作：进入 Badcase、归因和版本回归，不自动调 Prompt 或自动训练后上线。

### 12.5 告警去重与运维指导

- 相同 Scope、根因和时间窗的告警聚合为一个 Episode。
- 设置冷却期；新证据或严重度变化才重新通知。
- Episode 级告警噪声统计“聚合后仍被人工判为误报或低价值的 Episode”；【预期目标】相较 Baseline 下降至少 40%。
- 通知级重复统计“同一 Episode 在无新证据、无严重度变化时重复送达的通知”；【预期目标】相较 Baseline 下降至少 50%。

每条运维指导固定输出：

```text
现象
影响范围
关键证据及数据时间
最可能原因与替代解释
下一步验证步骤
临时缓解方式
禁止操作
负责人或升级对象
恢复判据
回滚办法
```

运维指导评测包括步骤可执行率、首步命中率、错误指导率和 MTTR。危险或不可逆的错误指导为 Critical Error，门槛为 0。

## 14. 常见评测偏差与解决办法

| 风险 | 会造成什么误判 | 解决办法 |
|---|---|---|
| 根因不是唯一 | 强制单选会惩罚合理诊断 | 多标签、证据和允许集合 |
| 只收告警正例 | Precision 虚高、不会拒答 | 加入 Quiet Negative 与误报样本 |
| 使用 T0 后数据 | 离线成绩虚高 | 冻结 Point-in-Time Snapshot |
| 把采纳当正确 | 学到人员偏好与选择偏差 | 专家盲审、受控实验、保留拒绝样本 |
| 上线后自然回落 | 把均值回归当收益 | 同期 Control、Switchback 或 DiD |
| 严重案例太少 | 总体准确率掩盖高风险漏报 | 单独报告严重 Recall，安全集合补测试 |
| Tool 结果随时间变化 | Replay 不可复现 | 保存脱敏快照、版本和响应 hash |
| Retry 触发重复副作用 | 审批或写入多次发生 | 持久化幂等键和最终状态查询 |
| LLM Judge 自证 | 评分偏向同类模型表达 | 程序规则和专家盲审为主 |
| 多个操作同时发生 | 无法归因阈值建议 | 预注册排除/记录规则和实验控制 |
| 版本混用 | 不知道改善来自哪里 | 模型、Prompt、工具、数据、Workflow 分别版本化 |
| 只看总体均值 | 长尾或小城市退化被掩盖 | 分层切片与最差组指标 |

## 17. 最终验收原则

城市异动诊断 Agent 的升级顺序必须是：

1. 数据可用且数值可追溯；
2. Read-only 诊断达到质量门槛；
3. 人工使用后确实更快且没有降低判断质量；
4. 建议通过规则、Dry Run、审批、幂等和回查；
5. 有同期对照地证明业务改善；
6. 最后才把目标数字改写为实际结果。

只要证据不足，正确输出就是 `ABSTAIN`、转人工或保持只读，而不是生成一个看起来完整的阈值调整方案。
