# 城市异动诊断 Agent：实施路线图与运维手册

> 状态：下一阶段执行计划
>
> 时间说明：下面以一名主负责人、可获得业务/数据/后端同事评审为假设，给出最早约 20 周的实施参考；阶段闸门优先于日历，数据、权限、样本或稳定观察不足时必须顺延。
>
> 两条交付线：“生产方案深化”和“个人合成数据作品”必须隔离。个人仓库只保留通用设计、合成数据和从零实现的示例，不复制公司代码、SQL、日志或数据。

## 1. 最小可行路线

如果时间有限，优先完成下面 8 周 MVP：

这里的 8 周路径是个人作品或离线原型彩排；其中的回放演示与 Shadow 框架 Dry Run 不代表已经进入正式 P5，也不能跳过正式评测样本、在线周期和严重案例闸门。

```text
第 1–2 周：业务访谈、人工流程 Baseline、指标/根因/动作契约
第 3 周：Episode、Evidence、Gold/Safety Set 和 Mock Tool
第 4 周：LangGraph 状态机、持久化和只读异常确认
第 5 周：有限假设、并行取证、证据引用和 ABSTAIN
第 6 周：运维 Runbook + 阈值 Dry Run，不提交生产
第 7 周：离线回放、轨迹评测、安全故障注入
第 8 周：Replay 演示、Shadow 运行框架 Dry Run、可观测 Dashboard 与继续/停止决策
```

这个 MVP 的完成定义不是“能聊天”，而是：

- 一个历史/合成 Episode 可以从快照完整重放；
- 每个节点和工具调用可观察；
- 任何数字都能定位 Evidence；
- 数据不足会 ABSTAIN；
- 阈值只生成 Dry Run；
- 进程重启后 Workflow 能恢复；
- 重放不会重复产生副作用；
- Gold Set 和 Safety Set 有自动评测报告。

如果在第 8 周仍无法证明事实正确、证据可追溯和危险动作数为 0，就不进入生产建议灰度。

## 2. 双轨交付策略

### 2.1 生产方案深化

生产轨需要真实组织权限和数据，只能在授权环境中实施：

- 接入真实指标、配置、运维和审批系统；
- 建立数据权限、审计、值班和发布流程；
- 与领域专家完成 Gold Set；
- Shadow、Pilot、Canary 和因果效果评估；
- 使用既有确定性动作服务执行。

### 2.2 个人合成数据作品

离开公司以后可以继续做一个完整但脱敏的可运行作品：

- 自己定义城市/区域/车辆的虚构 ID；
- 用合成时序生成需求突增、低电积压、数据延迟、服务故障等 Episode；
- 用 SQLite/PostgreSQL 保存案件、证据和 checkpoint；
- 用 Mock MCP/HTTP Tool 返回带数据水位的聚合结果；
- 用 LangGraph 实现同一 State、节点、审批暂停和恢复；
- 写一个只生成 Dry Run 的虚构阈值动作服务；
- 建立 30–50 个功能案例和 30 个安全/故障案例；
- 做本地 Dashboard 或命令行 Demo，展示 Trace、证据和回放评测。

个人作品不声称真实业务收益，但可以证明 Workflow、Eval、Durable Execution、Guardrail 和工程质量。若未来获得合法公开数据，可以替换合成数据继续实验。

## 5. P0：业务发现与 Baseline（最早第 1–2 周）

### 目标

不写代码，先把用户、问题、事实和验收标准讲清楚。

### 工作项

#### 业务访谈

至少访谈策略、运营、值班研发和审批人，每类 2–3 人；对最近 10–20 个案件做时间线复盘：

- 首个异常信号何时出现；
- 谁先发现、在哪发现；
- 查了哪些系统和指标；
- 哪一步等待最久；
- 有哪些判断分歧；
- 最终采取什么动作；
- 为什么没有采取其他动作；
- 何时认为恢复；
- 是否真正知道动作有效。

#### Baseline 采集

建立统一事件时间：

```text
T_detectable → T_alert → T_ack → T_evidence_ready
→ T_recommendation → T_product_review → T_downstream_approval
→ T_execution_final → T_recovery
```

记录：

- MTTD、MTTA、告警到证据/建议/执行/恢复；
- 人工分钟、查询数、系统数、沟通轮次；
- 告警数、去重后案件数、误报和漏报；
- 诊断/建议的编辑、拒绝和未知；
- 是否有最终执行状态、效果窗和回滚；
- 按严重度、城市规模和根因切片。

#### 契约评审

- 选定 1 个主异常指标和 2–3 个 Guardrail；
- 完成指标卡、数据 owner 和刷新 SLA；
- 根因 taxonomy 卡片分类；
- 定义动作风险等级；
- 定义 MVP 支持和不支持的 Scope；
- 预注册评测和灰度指标。

### 退出门槛

- [ ] 至少 10 个真实流程时间线被复盘；
- [ ] 主用户和最耗时步骤有证据；
- [ ] 指标公式、分子分母、时间和粒度无冲突；
- [ ] 首版 taxonomy 能覆盖样本，并保留 UNKNOWN；
- [ ] 明确“阈值动作不是默认答案”；
- [ ] 目标数字根据 Baseline 调整并签字/记录评审人。

## 6. P1：数据、Episode 与 Eval 地基（最早第 3–4 周）

### 工作项

1. 定义 Episode、MetricSnapshot、Evidence、Hypothesis、Evidence-Hypothesis Relation、ExpertLabel、Recommendation、Execution、Outcome Schema；
2. 保存 T0 时点快照和数据水位；
3. 开发数据/工具 Contract Test；
4. 按评测文档建立历史 Episode、Gold、Safety 与故障样本池；
5. 编写标注指南和代表性示例，按预注册比例双人标注并计算一致性；
6. 建立固定锚点集、时序盲测和整城留出；
7. 定义程序 Grader：Schema、Evidence、权限、规则和轨迹；
8. 定义专家盲审表，不让评审人看到“哪个是 Agent 输出”；
9. 在开发只读图前冻结最小共享契约：领域校验、配置版本语义、幂等键/状态枚举和稳定错误码；此时只做 Contract Test，不开放写权限。

### 退出门槛

- [ ] 任意 Episode 可在离线环境重放；
- [ ] T0 后信息不能进入诊断上下文；
- [ ] 关键数值能绑定 Evidence；
- [ ] 正常负例、未知和无需改阈值的样本均存在；
- [ ] 标注一致性达到规划门槛，否则先修标注指南；
- [ ] 评测脚本能生成带版本的报告。
- [ ] Python Workflow 与 Java 动作服务对最小共享校验、配置版本和幂等状态契约的 Contract Test 一致。

## 7. P2：Workflow 骨架（最早第 5–6 周）

### 工作项

- 创建 FastAPI 的建案、查询状态、人工恢复和健康接口；
- 用 Pydantic 定义外部输入、公开输出和每个节点边界对象，用带 Reducer 的 `TypedDict` 定义内部 Graph State；
- 构建 LangGraph `StateGraph` 与条件边；
- 使用 PostgreSQL Checkpointer，不用内存作为生产事实源；
- `case_id` 与 `thread_id` 稳定映射；
- 在外部 API、模型调用和副作用周围建立 Task 边界；
- 支持 `interrupt()` 和同一 thread 恢复；
- 写入 Trace、节点耗时、工具、Token、版本和错误类型；
- 实现 Budget：最大节点、模型调用、工具、Token 和总时长；
- 实现 deterministic replay 和固定工具响应回放；
- 注入重启、超时和重复恢复故障。

### 必测场景

- 节点完成后进程崩溃，重启从 checkpoint 恢复；
- Interrupt 前的节点重放，不重复发送通知；
- 同一恢复请求重复 10 次，最终状态一致；
- 模型结构化输出连续失败，系统降级而非死循环；
- 一个并行工具失败，其他结果保留并明确缺口；
- 超过预算，生成已有事实 + ABSTAIN。

### 退出门槛

- [ ] 所有需要恢复的节点输入输出可序列化和版本化，并由编排器按节点或 super-step 边界自动 checkpoint；
- [ ] 进程重启恢复演练通过；
- [ ] 无重复副作用；
- [ ] 所有路径都有结束或人工等待状态；
- [ ] 单案件能从 Trace 复原执行轨迹。

## 8. P3：Read-only 诊断 MVP（最早第 7–9 周）

### Week 7：DQ 与异常确认

- 接入数据水位和质量工具；
- 实现当前窗/基线窗比较；
- 实现异常持续、样本量和严重度规则；
- DQ Fail 单独路由；
- 非异常关闭并解释原因。

### Week 8：假设与取证

- Planner 最多提出 3 个 taxonomy 内假设；
- 每个假设指定支持与反证标准；
- 只允许白名单只读工具；
- 并行收集独立证据；
- 对结果做单位、窗口和新鲜度标准化；
- 有界补证循环最多 2 次。

### Week 9：根因与 Runbook

- 根因多标签排序；
- 置信度校准和 UNKNOWN；
- 每个数值自动查 Evidence 引用；
- 生成观察、升级和运维 Runbook；
- 创建通知/工单草稿但不发送；
- 建立人工反馈表。

### 退出门槛

- [ ] Gold/Safety Set 的 read-only 指标达到文档门槛；
- [ ] Critical 幻觉、越权和写工具调用为 0；
- [ ] 数据不足的案例可以正确 ABSTAIN；
- [ ] 根因报告包含支持、反证和未知；
- [ ] Runbook 危险/不可执行步骤为 0。

## 9. P4：阈值推荐与执行底座加固（最早第 10–12 周）

### Week 10：共享领域规则

- 抽取 Scope/实体归属校验；
- 统一当前配置查询；
- 建立阈值上下限、最大变化、冷却、禁止组合；
- 判断近期变更和在途审批；
- 推荐器只对 `THRESHOLD_MISMATCH` 且证据充分的案件工作。

### Week 11：Dry Run 与审批卡片

- 生成当前值/建议值/影响 Scope 的完整 Diff；
- 保存配置版本和 Dry Run 哈希；
- 计算候选区间和推荐值；
- 展示证据、风险、观察指标与回滚条件；
- 支持人工编辑后重新验证；
- 本阶段仍不提交生产动作。

### Week 12：可靠动作协议

- `request_id` 必填且唯一；
- 引入 `recommendation_version`；
- 持久化案件→建议→审批→执行→观察映射；
- 幂等键：案件 + 建议版本 + 动作 + Scope；
- 配置 Compare-and-set；
- 审批终态和执行终态分开；
- 事务化 Outbox 或可靠队列；
- 执行后回查与终态 API；
- 明确多条件原子/部分成功/补偿语义；
- 完成 Kill Switch 和只读降级。

### 退出门槛

- [ ] Dry Run、领域规则、权限和版本冲突达到评测文档规定的安全门槛；
- [ ] 重复审批/回调/执行不会重复写；
- [ ] 可区分产品审核、下游 submitted/pending/approved/rejected/expired，以及执行 applying/applied/failed/partial/unknown/rolled_back；
- [ ] 任何状态不明可以通过查询对账恢复。

P4 必须交付完整 Action Adapter：共享确定性校验、配置 Compare-and-set、持久化幂等、事务化 Outbox/可靠队列、可查询执行终态、补偿/回滚和 Kill Switch。该闭环在 P7 Canary 前必须通过集成与故障注入，不能以“已有审批接口”代替。

## 10. P5：Replay 与线上 Shadow（最早第 13–15 周）

### Week 13：历史 Replay

- 固定达到评测文档样本门槛的 Gold、Safety 与严重异常切片；
- 逐节点、轨迹、诊断、建议、安全和性能评测；
- 按城市规模/根因/严重度/DQ 切片；
- 与规则-only、小模型和强模型方案比较；
- 建立失败样本聚类和 owner。

### Week 14–15：Shadow

- 线上事件触发 Workflow，但输出不提交动作；
- 同时满足评测文档规定的最短运行周期、Episode 总量和严重异常切片；不足时顺延 P5；
- 与真实人工排查做盲评；
- 监控成功率、延迟、成本、工具失败和数据水位；
- 每天查看 `INC-P0/INC-P1`，每周做质量评审；
- 任一 Critical 安全问题立即停止 Shadow 的相关能力并回归。

### 退出门槛

严格以 [评测、灰度、SLO 与量化目标](04-评测灰度SLO与量化目标.md) 为准。Shadow 只证明在线可运行和诊断质量，不能证明业务收益。

## 11. P6：人辅 Pilot（最早第 16–17 周）

### 范围

- 选择满足代表性和权限边界的试点 Scope；
- 展示诊断、证据、Runbook 和阈值 Dry Run；
- 不自动提交审批；
- 审核量、严重样本和观察周期达到评测文档的 Pilot 门槛。

### 交互反馈

每次记录：

- 看过/未看；
- 有帮助程度 1–5；
- 接受/编辑/拒绝/补证；
- 编辑字段和原因；
- 人工额外查了什么；
- Agent 节省或增加多少时间；
- 最终根因、动作和效果。

### 退出门槛

- Critical unsafe = 0；
- 专家有帮助率达到规划门槛；
- 人工诊断时间相对 Baseline 显著下降；
- 无证据数值结论为 0；
- 告警负担没有增加；
- 拒绝/编辑集中问题已经有修复方案。

## 12. P7：审批 Canary（最早第 18–19 周）

### Eligible 条件

首批只允许：

- 低风险、单 Scope、单变量；
- 根因和证据达到高置信门槛；
- 当前配置存在且版本未变化；
- 无在途审批并已过冷却期；
- 变化在规则范围；
- Dry Run 完整且观察/回滚条件已定义；
- 人工明确批准。

### 灰度方式

- 从评测文档规定的最小流量档或少数 Scope 开始；
- 设置每日提交上限和单城市上限；
- 达到评测文档规定的早期零事故样本门槛并观察完整效果窗；
- 每次执行后自动对账；
- 高风险动作永久保留人审，不把“全量”理解成全自治。

### 立即停止条件

- 任一越权、跨 Scope、重复或无审计写入；
- 审批卡片与最终执行不一致；
- 配置版本冲突未阻断；
- 关键数据过期仍给建议；
- 敏感信息泄露；
- 回滚无法执行；
- 核心 Guardrail 超过预注册非劣界；
- 连续窗口 SLO 违约或状态无法对账。

停止后切换 read-only，保存所有 Evidence 和 Trace，按 `INC-P0` Runbook 处理。

## 13. P8：Scale、效果评估与扩量（最早第 20 周起）

优先对 eligible Episode 分层随机到 Agent 辅助和原流程；无法随机时使用阶梯 rollout、switchback 或匹配控制 + Difference-in-Differences，并检查 pre-trend。

报告必须包含：

- 研究周期、Scope 和 Episode 样本；
- 纳入/排除规则；
- Primary、Guardrail、效果窗和停止规则；
- Baseline 与同期对照；
- effect size、95% CI 和样本量；
- 人工修改、拒绝、回滚和失败；
- 适用城市/根因边界；
- 是否达到扩量门槛。

不能用单个成功故事、采纳率或普通前后对比决定扩量。

## 14. 测试策略

### 14.1 单元测试

- State reducer 和状态迁移；
- 严重度、预算和路由规则；
- 数据新鲜度、分母和缺失；
- 幂等键、版本比较和状态机；
- 阈值上下限、步长、冷却和冲突；
- Evidence 数值映射；
- 告警去重、抑制和升级。

### 14.2 Contract Test

- 每个工具 Schema 的向前/向后兼容；
- 单位、时区、窗口和枚举；
- 超时、无数据、过期、截断、权限错误；
- 指标服务与离线快照对账；
- Dry Run 与执行请求一致。

### 14.3 Workflow 测试

- 每条条件边至少一例；
- 多个正确轨迹而非只允许唯一调用顺序；
- 并行工具部分失败；
- 补证循环到预算上限；
- Human interrupt 后 approve/edit/reject/request_more_evidence；
- 旧 checkpoint 在新版本下的迁移/拒绝策略。

### 14.4 故障注入

- DB/Checkpointer 暂时不可用；
- 模型超时、限流和错误 Schema；
- 工具慢、返回冲突或改变结果；
- 队列重复和乱序；
- 回调重复 10 次；
- 执行成功但回执丢失；
- 回执成功但回查不一致；
- 部分成功后进程退出；
- Trace 系统失败但核心动作不能丢审计。

### 14.5 负载测试

以观测峰值和告警风暴建场景，而不是只压 API：

- 正常持续启动；
- 同时多个城市爆发；
- 慢 Hive 工具占用；
- 模型限流；
- 审批积压与集中恢复；
- 效果观察任务批量触发；
- 所有工具响应保存/重放时的吞吐。

初始容量门槛详见评测文档；压测后才能写“吞吐提升”和“P95 降低”。

## 16. 可观测性与 Dashboard

### 16.1 一案多段 Trace

Case 通过稳定的 `case_id/thread_id` 关联完整生命周期，但不让一个 Root Span 跨小时或数天保持开启。每次初始运行或恢复建立独立 Trace segment，并用 Span Link 关联前段；子 Span 包含本段实际发生的异常确认、Planner、Tool、Verifier、推荐、校验、审核、执行或观察。等待时长由 Wait Slot 时间戳计算；只记录 ID、Hash 和摘要，不默认记录敏感正文。

### 16.2 四个 Dashboard

#### 业务流程

- open/diagnosing/waiting/acting/observing 数量；
- MTTD/MTTA/到证据/到建议/MTTR；
- 按城市、根因和严重度切片；
- 告警→案件→建议→产品审核→下游审批→执行终态→恢复漏斗。

#### 质量

- DQ Gate、根因 Top-K、Evidence 正确率；
- ABSTAIN、专家评分、编辑和拒绝；
- Critical Badcase 和固定锚点回归；
- 不同模型/Prompt/工具版本对比。

#### 可靠性

- Workflow 成功、恢复、循环和超预算；
- Workflow admission rate、completed workflows/s、在途数和 oldest queue age；
- 节点/工具 P50/P95/P99；
- 队列年龄、重试和错误类型；
- 审批与执行对账、重复拦截、版本冲突；
- Outbox backlog 和效果任务延迟。

#### 成本

- 单案件模型调用、Token 和成本；
- 工具调用与数仓扫描成本；
- 大小模型路由比例；
- 缓存命中、无效/重复调用；
- 按根因和复杂度的成本分布。

## 17. 告警与当班响应

| 事故等级 | 触发示例 | 立即动作 | 恢复条件 |
|---|---|---|---|
| `INC-P0` | 越权/重复/无审计写入、执行与审批不一致、泄露 | Kill Switch、停写、人工接管、保全 Trace、通知安全/业务 owner | 根因明确、受影响范围对账、修复和回滚验证、负责人批准 |
| `INC-P1` | 关键数据过期、核心工具故障、队列堆积、执行终态未知 | 切 read-only、停止建议或降级、查询对账、通知系统 owner | 数据恢复、积压消化、状态可证、连续健康窗口 |
| `INC-P2` | 成本/延迟漂移、某根因质量下降、编辑率和噪声升高 | 建治理工单、缩小 Scope、回归评测 | 版本修复通过锚点/安全集并观察稳定 |

告警必须有 owner、响应 SLA、去重键、升级规则和 Runbook 链接。没有 owner 的告警等于没有告警。

## 18. Runbook

### 18.1 关键数据源过期

1. 确认是单 Scope、单数据域还是全局；
2. 比较 expected watermark 与实际 watermark；
3. 停止使用该数据源生成阈值建议；
4. 已在运行的案件标记 `DEGRADED`；
5. 只输出此前已验证事实和缺失项；
6. 通知数据 owner 并记录预计恢复时间；
7. 恢复后重新执行 DQ Gate，不从旧中间状态直接写动作；
8. 将事件加入 DQ 安全集。

### 18.2 模型服务不可用

1. 检查限流、超时、配额和版本；
2. 不自动无限重试；
3. 简单任务可路由备用模型，前提是已过同一安全集；
4. 否则返回确定性异常摘要和 Evidence；
5. 保持案件可恢复，不丢已查询结果；
6. 不因模型故障绕过产品审核、下游 BPM 或执行前重验；
7. 恢复后从 checkpoint 继续。

### 18.3 工具慢或部分失败

1. 标记具体工具和 Evidence 缺口；
2. 独立分支结果保留；
3. 只读幂等工具按退避策略有限重试；
4. 有替代工具且口径一致时才降级；
5. 缺失关键证据时 ABSTAIN；
6. 不用历史数据假装当前结果；
7. 记录工具 SLO 和 Badcase。

### 18.4 审批通过但执行终态未知

1. 冻结同一 Scope 新建议；
2. 根据幂等键查询动作记录和当前配置；
3. 不盲目重放写请求；
4. 对账审批版本、Dry Run 哈希和配置版本；
5. 确认未执行、成功、失败或部分成功；
6. 按状态继续执行、补偿或人工处理；
7. 回传最终状态并记录根因；
8. 只有状态可证后解除冻结。

### 18.5 重复回调或重复恢复

1. 通过持久化幂等键查找已有结果；
2. 返回相同终态，不重新产生副作用；
3. 记录重复来源和次数；
4. 如果 payload 与同一幂等键不一致，拒绝并告警；
5. 对照最终配置验证没有重复变化。

### 18.6 Guardrail 恶化

1. 停止相同策略/Scope 的新提交；
2. 校验数据质量和效果窗；
3. 比较控制组及同时发生的其他动作；
4. 达到预注册回滚条件时生成人工回滚建议；
5. 高风险场景由值班/审批人执行回滚；
6. 持续观察恢复；
7. 将案件加入 Critical Badcase，相关版本不得继续扩量。

### 18.7 成本或 Token 激增

1. 按模型、节点、根因和工具切片定位；
2. 检查循环、重复工具、大结果和 Context 未裁剪；
3. 收紧预算并切换只读/简化报告；
4. 缓存只允许复用口径和 Scope 完全一致且未过期的结果；
5. 修复后比较质量，不能只为降成本牺牲安全和诊断；
6. 达到日预算阈值时停止深诊断，保留快速路径。

## 19. 降级矩阵

| 故障 | 仍可提供 | 必须关闭 |
|---|---|---|
| 一个非关键数据工具失败 | 已验证事实、其他分支、明确缺口 | 依赖该证据的结论和动作 |
| 关键数据过期 | DQ 告警、历史背景（明确过期） | 当前阈值建议 |
| LLM 不可用 | 确定性检测、原始指标摘要、人工接管 | 新的自由诊断文本 |
| Checkpointer 不可用 | 接入层拒绝新建案或排队 | 无状态临时跑完整 Workflow |
| 审批系统不可用 | 诊断和 Draft | 所有生产动作 |
| 动作服务终态未知 | 状态查询、Scope 冻结 | 重复提交和相同 Scope 新建议 |
| Trace 平台不可用 | 本地最小审计/队列 | 无审计写入 |
| 效果系统不可用 | 动作终态和手工观察任务 | 自动宣称建议有效 |

降级必须 fail closed：安全或事实不确定时减少能力，不增加自治。

## 22. 风险登记表

| 风险 | 早期信号 | 预防 | 触发后处理 |
|---|---|---|---|
| 没有真实用户问题 | Demo 很丰富但没人看或使用 | P0 观察真实案件 | 缩 Scope，回到最高耗时一步 |
| 数据口径冲突 | 专家对同一数字争论 | 指标契约、owner、对账 | 标记 DQ，停止动作建议 |
| 工具过细/过多 | 模型调用长、重复、难评测 | 领域化高层工具 | 合并工具并跑轨迹回归 |
| 根因强制单选 | 多因案件误判 | 多标签 + UNKNOWN | 加反证和仲裁样本 |
| 采纳率虚高 | 只收被采纳样本 | 阴性/拒绝/随机抽样 | 盲审和控制实验 |
| 微调过早 | 没有稳定错误簇 | 先 Eval/Tool/Prompt | 停训练，补数据契约 |
| 状态不可靠 | 重启后重复动作 | Checkpoint、Outbox、幂等 | 切 read-only 并对账 |
| Agent 成本失控 | 循环和上下文持续增长 | Budget、摘要、大小模型路由 | 停深路径，修复后回归 |
| 业务收益错归因 | 异常自然恢复也算收益 | 对照/随机/DiD | 降级结论等级，重做实验 |
| 个人作品泄密 | 复用内部数据/命名 | 合成数据、从零实现 | 立即移除并做仓库历史审计 |

## 24. 下次开始实现时的第一周清单

如果未来在另一台电脑继续，先做：

1. 阅读本目录六份文档和事实台账；
2. 决定做“生产方案深化”还是“个人合成数据作品”，不要混用资产；
3. 选择一个主异常场景，不要一开始覆盖全部 taxonomy；
4. 写 10 个 Episode，其中至少 3 个非异常、2 个 DQ、2 个无需改阈值；
5. 定义 State、Evidence 和三个只读 Mock Tool；
6. 实现最小链路：API 原子建案 → 初始化图 → DQ → 异常确认 → 取证 → 报告 → 产品审核；
7. 用 PostgreSQL Checkpointer 验证中断和重启恢复；
8. 写 10 个自动 Grader 和 10 个故障测试；
9. 录一个 5 分钟 Demo：正常诊断、证据不足拒答、重启恢复各一例；
10. 更新本文件中的实际进度，仍未实现的能力继续标记为“待建设”，数字保留【规划门槛】或【预期目标】。

这十步完成后再增加阈值推荐、MCP、多个数据域或多 Agent，避免把项目做成只有架构图、没有可评测闭环的“技术集合”。
