# 城市异动诊断 Agent：产品目标与业务能力

> 状态：完整产品规划
>
> 前提：截至 2026-09-04，城市异动发现、诊断和效果闭环尚未实现；本文描述的是目标能力，正式效果或验收目标数字必须使用【规划门槛】或【预期目标】。访谈数、案例数等工作预算不代表效果目标。
>
> 核心原则：先让人更快、更可靠地做决定，再讨论低风险自动化；阈值调整只是多个处置选项之一。

## 1. 产品一句话定义

目标产品形态将是面向策略、运营和值班人员的“异常案件工作台”：持续观察城市/区域经营指标，把告警聚合成案件，自动完成数据质量检查、异常确认、有限假设取证和根因排序，并输出有证据、有风险边界、可审批、可回看的处置建议。

它不是：

- 一个能随意查询所有大表的聊天机器人；
- 一个只会把告警换成自然语言的摘要器；
- 一个看到指标跌了就自动改阈值的自治系统；
- 一个以调用大模型次数或调整次数为成功指标的 Demo。

## 2. 为什么值得做

### 2.1 需要先验证的业务痛点

当前材料能证明阈值动作底座存在，但没有足够证据证明以下痛点的真实数值，因此先列为【待测基线】：

| 痛点假设 | 可能表现 | P0 如何量化 |
|---|---|---|
| 异常发现慢 | 指标已经持续恶化，才被群消息或投诉触发 | 记录 `T_detectable` 和 `T_alert`，计算 `MTTD = T_alert - T_detectable` |
| 告警噪声高 | 同一问题重复通知、数据延迟也被当成业务异常 | 统计每城市日告警数、去重后案件数、有效告警比例和被静默比例 |
| 排查路径依赖个人 | 资深人员知道查什么，新人反复问口径、找 SQL | 对每个案件记录查询次数、沟通轮次、人工分钟和参与角色 |
| 证据分散 | 指标、配置、运维、服务状态在不同系统 | 统计形成完整结论所需系统数、复制粘贴次数和证据缺失率 |
| 处置不一致 | 相似异常被不同人员采用不同阈值或运维动作 | 对历史相似案件比较建议方向、幅度、审批修改率和后验结果 |
| 审批不等于落地 | 流程批准后，执行失败或最终值无法快速确认 | 统计审批到终态耗时、状态不明比例、重复提交和回查缺失 |
| 效果没有回收 | 改完以后没有固定观察窗或对照 | 统计有 T+结果、有 Guardrail、有对照说明的案件比例 |
| 经验无法复用 | 复盘散落在聊天或个人脑中 | 统计有结构化根因、证据、动作、结果和复盘的案件比例 |

P0 必须同时满足[评测文档](04-评测灰度SLO与量化目标.md)定义的最短周期、代表性场景和样本门槛；严重样本不足就延长。真实基线出来后再锁定目标，禁止倒推一个更好看的“旧流程耗时”。

### 2.2 北极星指标

建议的北极星是：

> **符合纳入标准的真实异常中，从首次可检测到形成安全、可审阅处置方案的时间，及其在不恶化业务 Guardrail 前提下的恢复效果。**

它由四类指标共同约束：

1. 发现质量：严重异常召回、误报、重复告警和检测延迟；
2. 诊断质量：根因、关键证据、拒答和专家有帮助率；
3. 决策安全：越权、越界、重复动作、版本冲突和回滚能力；
4. 业务价值：人工时间、MTTA/MTTR、异常持续时间或异常面积。

不能把“建议采纳率”单独当北极星。运营可能因权限、资源或习惯拒绝正确建议，也可能采纳一个后来无效的建议。

## 3. 目标用户和决策场景

| 用户 | 需要解决的问题 | Agent 交付物 | 不替用户做的事 |
|---|---|---|---|
| 城市运营 | 发生了什么、先做哪一步、找谁处理 | 异常摘要、证据、Runbook、工单草稿 | 不代替现场确认和资源调度 |
| 策略/算法 | 是策略问题还是供需/数据/服务问题，阈值是否应调 | 根因排序、配置 Diff、候选区间、模拟和效果窗 | 不让 LLM 自由决定生产数值 |
| 值班研发 | 是否是服务、数据或发布问题，如何止损 | DQ/服务告警、变更关联、排查步骤和升级路径 | 不自动执行高风险运维命令 |
| 审批人 | 为什么要改、风险多大、失败后如何回退 | 完整审批卡片、证据链接、当前/建议值、Guardrail | 不把自然语言摘要替代确定性校验 |
| 产品/管理者 | 哪些城市反复异常、效率和效果是否改善 | 周报、趋势、Top 根因、处理漏斗和对照结果 | 不用未经控制的前后对比宣称因果收益 |

## 4. 典型用户旅程

### 4.1 告警驱动

```text
指标异常事件
→ 系统聚合/去重为案件
→ 检查数据新鲜度与分母
→ 确认异动范围和严重度
→ 查供需/车辆/换电/配置/运维/服务证据
→ 输出根因 Top-K、反证和未知项
→ 路由到观察、运维、升级或阈值建议
→ 人工审批/处置
→ 观察效果并关闭
```

### 4.2 定时健康巡检

- 每个业务刷新周期运行轻量确定性检查；
- 只对超过严重度和持续时间门槛的 Scope 建案；
- 同类事件合并，不对每个指标点启动一个 Agent；
- 每日生成“新发、持续、恢复、需要关注”的城市健康摘要；
- 如果数据源延迟，只生成数据质量事件，不生成业务根因结论。

### 4.3 人工提问

用户可以问“为什么某城市最近低电车辆积压”，但系统仍然要：

1. 解析并校验城市、区域、车型、指标和时间窗；
2. 明确数据截止时间；
3. 先做异常确认，而不是默认用户假设正确；
4. 把这次分析挂到已有案件，或建立新的手工案件；
5. 输出证据引用和未知项，而不是只返回流畅文本。

### 4.4 变更后观察

- 审批和执行完成后创建观察任务；
- 在业务确定的多个窗口比较 Primary 和 Guardrail Metric；
- 识别数据延迟、自然回落、同时发生的其他动作和外部事件；
- 触发“继续观察、恢复正常、建议回滚、升级人工”之一；
- 即使未执行阈值，也观察 Runbook/运维动作后的结果。

## 5. 产品 Scope

### 5.1 首版必须覆盖

- 单城市或单运营区的单次异常案件；
- 明确时间窗和基线窗；
- 只读数据质量与异常确认；
- 有限的根因分类和证据收集；
- 阈值建议、运维指导、继续观察、升级人工四类结果；
- 所有数值结论有证据引用；
- 阈值建议只做 Dry Run，不直接执行；
- 人工对诊断、证据和建议进行查看、编辑、拒绝或补证；
- 全链路 Trace、案件状态和离线重放。

### 5.2 第二阶段扩展

- 多指标/多区域关联和城市级聚合；
- 天气、节假日、活动、发布和服务事故的外部上下文；
- 小范围审批提交及执行终态回传；
- 自动生成工单和通知草稿；
- 历史相似案件检索；
- T+效果观察、Badcase 和周度评测；
- 城市风险趋势和重复问题治理。

### 5.3 明确不做

- 模型直接连接生产数据库执行任意 SQL；
- 未审批调整生产阈值；
- 未经权限检查跨城市查询；
- 让微调模型替代实时数据、业务规则、审批或幂等；
- 首版同时建设多个相互对话的自治 Agent；
- 为了展示技术而加入与诊断结果无关的复杂编排；
- 把内部源码、真实数据、表名或接口细节带入个人项目仓库。

## 6. 异常分类体系

根因应允许多标签，并区分 `primary` 与 `supporting`。下面是首版 taxonomy；真正使用前要与业务专家做 20–30 个案例的卡片分类校准。

| 一级根因 | 典型现象 | 关键证据 | 常见动作 | 应避免的误判 |
|---|---|---|---|---|
| `DATA_QUALITY` | 指标突变但多个业务侧不一致 | 数据水位、缺失率、分母、重复、上下游对账 | 告警数据负责人、暂停业务结论 | 把数据延迟当成真实供需异常 |
| `DEMAND_SURGE` | 需求突然增加，供给跟不上 | 订单/骑行请求、历史季节性、活动、天气 | 运力补充、动态运营、观察阈值适配 | 只看绝对量，不看基线和样本量 |
| `VEHICLE_SUPPLY_SHORTAGE` | 可用车不足、分布不均 | 可用车、调度、区域热力、车辆状态 | 调度/补车/区域平衡 | 把低电积压全归因于阈值 |
| `LOW_BATTERY_ACCUMULATION` | 低电车辆持续堆积 | 电量分布、进入/退出速率、换电能力 | 运维增援、换电策略或阈值评估 | 忽略换电站/人员容量瓶颈 |
| `SWAP_CAPACITY` | 待换量高但完成能力下降 | 人员、站点、设备故障、每小时处理量 | 恢复设备、排班、临时分流 | 用配置调整掩盖物理容量不足 |
| `WORK_ORDER_BACKLOG` | 工单进入、流转或完成出现积压 | 创建/接单/完成漏斗、处理时效、积压年龄 | 排班、流转修复、优先级和容量治理 | 只看未完成总量，不看到达与完成速率 |
| `DISPATCH_OR_POLICY` | 策略变化后局部异常 | 策略版本、变更时间、控制/实验差异 | 回滚策略、修正规则、观察 | 把相关时间点直接当因果证据 |
| `THRESHOLD_MISMATCH` | 当前阈值与供需/能力不匹配 | 当前/历史配置、边际响应、同类城市 | 生成受约束阈值建议 | 没有当前值和效果预测就自由拍数 |
| `WEATHER_OR_EVENT` | 特定时间/区域异常 | 天气、节假日、活动和历史同期 | 临时运营方案、增强监控 | 外部数据不可用时凭常识猜测 |
| `UPSTREAM_SYSTEM` | 服务/数据链故障导致业务表象 | 服务健康、错误率、发布和依赖状态 | 值班升级、降级、修复 | 在系统故障期继续提交策略修改 |
| `MULTI_CAUSE` | 多个因素共同作用 | 多分支证据与时间顺序 | 分阶段组合动作 | 强制挑一个唯一根因 |
| `OTHER` | 有证据但不在当前 taxonomy | 专家说明、支持与反证 | 转人工确认，评审是否扩展 taxonomy | 未评审就临时创造大量新标签 |
| `UNKNOWN` | 证据不足或相互冲突 | 缺失项、冲突项、查询失败 | ABSTAIN、转人工或补证 | 为了完成报告编造根因 |

## 7. 异常检测与严重度

### 7.1 检测不是 LLM 的工作

首版检测采用分层组合：

1. 硬规则：明显越界、持续未更新、分母为零、服务错误；
2. 稳健统计：中位数/MAD、分位数、EWMA、季节性同期偏差；
3. 变化点：持续结构变化，而不是单点尖峰；
4. 可选轻量监督模型：只有标签足够且显著优于规则时使用；
5. 业务聚合：把多个指标事件合并成一个 Episode。

模型只接收检测结果、窗口统计和证据摘要，不接收无限长的原始时序并凭视觉印象判断。

### 7.2 严重度建议

严重度由确定性评分计算，考虑：

- 影响 Scope 数量与业务量；
- 指标偏离幅度和持续时间；
- 是否影响核心 Guardrail；
- 数据可信度；
- 是否存在可逆动作；
- 是否与正在进行的变更或故障相关；
- 是否已经有相同案件处理。

| 等级 | 含义 | 首期响应方式 |
|---|---|---|
| S0 | 核心业务指标大范围、持续或不可逆地恶化，需要立即业务止损 | 最高优先级诊断、通知业务值班并人工接管；是否停写由独立安全策略决定 |
| S1 | 大范围或持续严重业务异常 | 高优先级诊断，必须人工确认处置 |
| S2 | 局部且可控异常 | 正常诊断，提供建议与观察窗 |
| S3 | 低影响、短时或低置信信号 | 聚合到摘要，满足持续门槛再建案 |
| DQ | 数据质量异常 | 独立路由，不生成业务动作建议 |

## 8. 输出和动作契约

### 8.1 每份诊断报告必须包含

```yaml
case_id: 脱敏案件标识
scope: 城市/区域/车型/时段
trigger: 触发指标、时间和检测器版本
data_cutoff: Agent 可见数据截止时间
anomaly:
  confirmed: true | false | unknown
  severity: S0 | S1 | S2 | S3 | DQ
  deviation: 带单位和基线的结构化值
root_causes:
  - label: 根因枚举
    role: primary | supporting
    confidence: 校准后的区间或等级
    supporting_evidence: [evidence_id]
    counter_evidence: [evidence_id]
unknowns: 尚缺信息和影响
recommended_actions:
  - type: MONITOR | OPS_GUIDANCE | ESCALATE | THRESHOLD_CHANGE | ROLLBACK
    rationale: 对应证据
    owner: 建议负责人角色
    risk: L0 | L1 | L2
    prerequisites: 执行前条件
    observe_until: 观察窗口
    rollback_when: 回滚条件
decision: proceed | request_more_evidence | abstain | close
```

### 8.2 阈值建议卡片

阈值卡片必须同时展示：

- 当前配置与读取时间；
- 建议配置、变化方向、绝对值和相对幅度；
- 生效 Scope、时段和有效期；
- 计算候选值的确定性规则/优化器版本；
- 支持证据与反证；
- 预计影响、风险和最坏情况；
- 业务上下限、变化速率、冷却期和冲突检查；
- Dry Run 影响范围和完整 Diff；
- 建议生成时的配置版本；
- 审批后观察窗、Primary/Guardrail Metric 与回滚条件。

这里描述的是产品审核操作，固定为 `approve`、`edit`、`reject`、`request_more_evidence`。`edit` 后必须产生新的不可变建议版本并重新经过全部确定性校验，不能把人工输入默认当安全。产品审核通过只允许创建动作预留，不等于下游 BPM 已批准，更不等于配置已生效。

### 8.3 运维指导 Runbook

```yaml
symptom: 现象
impact_scope: 影响范围
evidence: [evidence_id]
most_likely_cause: 当前最可能原因
verification_steps:
  - 步骤、预期现象、失败后下一步
mitigation:
  - 临时缓解动作、负责人和风险
do_not_do:
  - 在当前证据下禁止的动作
escalation:
  owner: 角色或团队
  condition: 何时升级
recovery_criteria: 恢复判据
rollback: 回滚办法
```

首期 Runbook 只提供查询、确认、沟通和可逆缓解建议。涉及生产命令、数据修复或配置写入时必须跳到对应受控系统和人工流程。

## 9. 产品功能模块

### 9.1 案件中心

- 列表按严重度、状态、城市、根因和负责人筛选；
- 展示从触发到关闭的完整时间线；
- 相同事件自动关联而不是重复建案；
- 清晰标记数据截止时间、Agent 版本和是否处于降级模式；
- 支持人工合并/拆分案件，并保留审计；
- 支持“我不认可这个根因/建议”的结构化反馈。

### 9.2 证据面板

- 一条结论对应哪些证据和反证；
- 每条证据展示来源、窗口、单位、查询条件、更新时间和质量标记；
- 原始大结果保存在受控证据存储，页面只展示摘要和下钻链接；
- 过期、截断、冲突证据显著标红；
- 支持对某条证据提出复查而不必重跑整个案件。

### 9.3 决策工作台

- 对比不行动、运维动作和阈值动作的预期收益/风险；
- 显示建议生成逻辑和硬约束，而不是只展示模型置信度；
- 支持修改候选动作并重新 Dry Run；
- 显示是否有在途审批、近期变更或冷却期；
- 分开展示产品审核、动作投递、下游 BPM、真实执行和最终回查，不用一个 `approved` 覆盖全部状态。

### 9.4 健康摘要与治理

- 日报：新发/持续/恢复异常、最重要城市、未处理 S1/S2；
- 周报：Top 根因、重复案件、平均处理耗时、采纳/编辑/拒绝、工具和数据故障；
- 月报：策略收益、Guardrail、回滚、跨城市漂移和模型/Prompt 版本变化；
- 告警治理页：误报、重复、被抑制、静默规则和冷却时间；
- 经验治理页：过期 Playbook、低质量案例和待仲裁标签。

## 10. 告警和通知设计

### 10.1 三层告警

这里是系统事故等级，与业务异常严重度 `S0/S1/S2/S3/DQ` 分开。

| 事故等级 | 示例 | 自动动作 |
|---|---|---|
| `INC-P0` | 越权/重复/无审计写入、敏感信息泄露、核心 Guardrail 严重恶化 | Kill switch，切 read-only，通知值班并保全证据 |
| `INC-P1` | 关键数据过期、核心工具失败、队列严重堆积、Workflow SLO 连续超标 | 停止生成可执行建议，只输出已证实事实并转人工 |
| `INC-P2` | 成本漂移、某根因精度下降、编辑率上升、低严重度噪声变多 | 进入日/周治理队列，不打断正在处理的安全案件 |

### 10.2 去重和升级

- 去重键包含 Scope、异常类型、检测器版本和滑动时间窗；
- 事件强度或影响范围扩大时更新原案件，而不是另发相同通知；
- 恢复事件只在异常持续过约定门槛后发送，避免抖动；
- 被抑制事件仍写审计，便于评估是否误抑制；
- 超过 SLA 未确认的 S1 自动升级，但不绕过审批执行动作；
- 通知文本只含必要摘要和受控链接，不携带敏感原始数据。

## 11. 量化价值假设

这里定义价值方向，不重复维护具体数值：

- 【预期目标】提升严重异常发现能力，并分别降低聚合后的 Episode 级噪声和通知级重复；
- 【预期目标】缩短 MTTD、MTTA、证据就绪和可审核建议形成时间，减少每个 Episode 的人工分钟；
- 【规划门槛】证据、数值、Scope、版本和最终执行状态均可追溯；
- 【规划门槛】越权、重复、无审计、错误写入和数据质量失败时仍建议属于硬停止事件；
- 【预期目标】在有同期控制的实验中缩短异常持续时间或异常面积，且业务 Guardrail 不劣化。

P3 先证明只读事实和建议质量，P6 证明人机协作价值，P7/P8 才验证执行可靠性和受控业务效果。具体目标、样本门槛、置信区间与 `INSUFFICIENT_EVIDENCE` 只以[评测、灰度、SLO 与量化目标](04-评测灰度SLO与量化目标.md)为准。

## 12. 一个端到端示例

假设某城市上午某区域的低电车辆占比连续三个刷新周期显著高于同期基线。

1. 检测器生成事件，系统发现已有相同 Scope 案件，更新而不重复通知；
2. 数据质量节点确认分区已完成、分母稳定、多个来源对账无明显冲突；
3. 确定性节点确认偏离幅度、持续时间和影响车辆数达到 S2；
4. Planner 只提出三个假设：需求突增、换电能力下降、当前阈值不适配；
5. 三个只读分支并行取证，并额外检查近期发布/服务故障作为反证；
6. 证据显示需求正常、换电站能力下降且部分区域配置偏紧；
7. 根因标记为 `SWAP_CAPACITY(primary) + THRESHOLD_MISMATCH(supporting)`；
8. 系统先生成运维恢复能力 Runbook，同时只对证据充足的小 Scope 计算临时阈值候选；
9. 推荐器根据规则给出候选区间，Dry Run 显示影响范围，Guardrail 检查通过；
10. 人工选择只执行运维动作、暂不调阈值，系统记录拒绝原因；
11. 两小时后能力恢复，指标下降；系统不能因此声称阈值策略有效，而应记录“未执行阈值、运维动作后恢复”；
12. 案件进入 Gold/Badcase 候选，用于验证 Agent 是否正确识别了“不是只靠阈值解决”。

这个示例体现了产品价值：不是增加阈值调整次数，而是减少错误调整，并让判断过程可复盘。

## 13. 产品验收问题

每个版本评审时必须回答：

1. 用户是谁，他原来哪一步最耗时？
2. Agent 输出改变了哪个具体决策，而不是只多了一份报告？
3. 每个关键结论能否回到当时可见的数据快照？
4. 数据不足时是否真的会停，而不是生成合理化解释？
5. 非阈值根因能否正确路由到运维、数据或研发？
6. 人工修改/拒绝是否被结构化记录并进入评测？
7. 产品审核、下游审批、执行、回查和效果是否是五个分开的状态？
8. 同一请求重试、服务重启或回调重复时，会不会产生重复动作？
9. 提升是否来自同期对照，而不是异常自然恢复？
10. 这些结果中，哪些已经测得，哪些仍只是目标？

只要这十个问题中有关键项回答不清楚，就不应扩大生产写权限。
