## 二、换电时效预测

### 11. 这个项目到底预测什么？

预测从首次派发到下一个关键用户事件的分钟数：换电前发生扫码拦截则取拦截；否则取换电后首个正常订单。它用于运维优先级，不是纯粹的换电完成 ETA。

### 12. 为什么 Label 设计这么复杂？

业务真正关心用户风险，但没有拦截的工单也需要有目标，于是引入换电后首单。代价是长尾同时受需求和运维过程影响，产生混合机制和删失问题。

### 13. 为什么只看 15–23 点？

这是模型生效和正式验收窗口；非高峰不少城市使用固定 3/4/5 小时策略。全天混算会把模型与规则混在一起，无法归因。

### 14. 为什么用 log label？

Label 长尾很重，log 可以稳定训练、减弱极大值支配，但会压缩长尾。必须同时看原尺度 MAE、bias、六桶和排序，而不是只看 log loss。

### 15. 你如何发现早期模型预测塌缩？

比较真值/预测均值、bias、长桶通过率和六桶预测单调性。真值均值 189.68、预测仅 35.87，`>75` 分钟通过率 0.23%，说明损失和权重把输出压向短时。

### 16. 为什么随机 test 不够？

相邻日期共享城市、季节和供需分布，随机拆分会过度乐观。日期 OOT 才模拟真正未来数据；参与调参后的 OOT 也不能继续当最终独立验收。

### 17. MAE 75.60 为什么是假提升？

不同表复用了同一事件类型编码，但编码对应的业务语义发生变化，长尾占比大幅下降。通过分桶贡献、分布重加权和同工单对照证明模型没有实现对应幅度的能力跃升。

### 18. 115 维减到 35 维怎么验证？

不是只看 importance，而是在同一随机集和未来 OOT 对比 MAE、严格率、六桶排序。35 维 OOT 相对 115 维 MAE 只回退约 0.42 分钟，严格率略升，才作为重构底座。

### 19. 新增 52 维中什么最有效？

permutation 表明新增 52 维整体打乱后 MAE +7.53，geo7 H-1 单块 +5.17，城市日级仅 +0.42。短时供需和订单热度比静态城市均值更有价值。

### 20. 城市差异明显，为什么不拆模型？

车均单与城市 P25 相关，但三组模型真实路由只改善 0.1165 分钟，短桶还退化。相关性存在不等于拆模值得；全国模型已吸收部分城市信息。

### 21. 为什么 custom 更好却选 linear？

只好约 0.25 分钟，但上线是 XGBoost 0.90 Java。linear 格式和解释更稳定；等配置 CPU 重训相对 GPU 只退 0.0959 分钟，风险收益更好。

### 22. 如何保证没有特征穿越？

固定 S-1、S-2、H-1 合同；训练 15–22 点读取 14–21 点完整快照；线上 TTL 与历史回放分表；用真实分区核对上游时间和值一致性。

### 23. 缺失特征怎么处理？

线上特征读取异常、结构错误或单值非数字时使用与训练一致的缺失策略，并为关键实时特征保留命中标志。优点是服务可用且口径一致，缺点是默认 0 可能与真实 0 混淆，因此还要监控命中率并逐步完善 missing flag。

### 24. 如何做灰度、回滚和版本控制？

把模型版本与城市范围配置化，先在有限城市验证输入完整性、线上延迟和分层指标，再逐步扩大范围。回滚不依赖重新发版，而是恢复上一稳定版本；面试时重点讲清触发条件、负责人和验证指标，不需要背具体配置键。

### 25. 如何保证在线特征和训练特征一致？

为每个特征明确来源、时间截点、缺失语义、类型和默认值，训练与在线复用同一份特征契约；上线前用固定样本逐字段比对，并持续监控缺失率、数值分布和预测漂移。发现差异时先定位数据快照和预处理，而不是直接归因于模型。

### 26. 模型与业务规则如何协同？

模型负责连续预测，规则负责不可违反的业务约束和特殊场景。规则应有清晰优先级、命中原因和审计记录，并通过离线回放评估它对模型收益的影响；避免让规则长期掩盖模型或数据问题。

### 27. 线上线下 9 分钟差异怎么排？

按模型 SHA、树数、特征顺序、完整向量和 Redis 快照逐层排。固定同一次向量后差异只剩 0.399 分钟，原差异来自不同小时快照。

### 28. 业务效果怎么样？

最强模型归因是同工单 MAE -2.30%，196/228 城改善，主要改善 2h+；严格率基本持平且 30–60m 退化。上线前后城市结果没有一致大幅改善，只是描述性观察，不能宣称因果。

### 29. 为什么没有达到 80%？

目标对混合事件和长尾很严格，预测时缺少运维 ETA、路线、前置任务、分钟级扫码和电量动态等关键信号。模型有排序能力，但点预测对 6–12h 仍低估。应补数据而非继续堆复杂 loss。

## 三、阈值智能调整系统

### 30. 为什么不用 LLM 直接生成 SQL？

这是高风险配置。LLM 不持有 DB 权限，只生成领域命令；权威实体范围、Java 业务规则、预查询、BPM 和固定 MyBatis 共同决定最终写入。

### 31. RAG 在这里是什么？

更像实体知识增强：LLM 提取候选城市，再从权威实体服务获取城市、运营区和车型范围。它不是通用向量文档检索，核心目标是实体消歧和作用域校验。

### 32. 如果提取城市的 LLM 就错了怎么办？

后续实体知识查不到会进入缺失/不匹配，不允许执行；更稳设计可以用词典/别名主数据先匹配、LLM 作为候选，并在多城市范围不确定时向用户确认。

### 33. Java 校验是 JSON Schema 吗？

当前准确说法是对象转换、程序化结构检查和手写领域规则；没有独立成熟 JSON Schema 引擎证据。

### 34. temperature=0 为什么还会错？

采样温度低不代表整个服务确定：模型推理、服务路由、上下文和截断仍可能造成差异，复杂指令也会产生系统性漏项。因此需要金标、覆盖校验和安全阻断。

### 35. 如何定义 LLM 正确率？

分层：严格 JSON → 可转换结构 → 字段/功能等价 → 业务语义 → Java 校验后结果 → 是否安全阻断。对于多指令还单独看覆盖率；延迟、截断和重试成本也必须报告。

### 36. 42 条是不是太少？

是，小样本只能用于领域回归和候选比较，不是长期 SLA。价值在于覆盖高风险边界并保留 239 次调用轨迹；下一步应从线上 Badcase 持续扩充、分层抽样并做版本化回归。

### 37. 为什么拆长期基础、周期调整和日期特例？

分别表达长期基础策略、周期性人工调整和指定日期特例；可以保留原始基础值并定义覆盖顺序，避免所有语义挤在一份 JSON 中相互污染。

### 38. 相对调整与绝对调整怎样区分？

绝对调整可以直接校验目标值；相对调整必须读取当前生效配置，再计算修改后的目标值。请求对象要显式区分两种语义，预览展示计算前后值，执行层只接收校验完成的确定结果。

### 39. 为什么修改前一定要 query？

因为相对值、覆盖层和车型回退都依赖当前真实配置。预查询让用户确认作用范围和基准；最终 query 则证明异步审批后实际状态。

### 40. 如何避免修改一个车型覆盖其他车型？

DB upsert 替换整列 JSON，所以必须完整读取、定点修改、保留其他车型和未知字段，再整体回写；局部 API 不等于局部数据库更新。

### 41. 多 condition 如何保证原子性？

当前按顺序执行，未看到请求级显式事务，存在部分成功风险。这是边界。合理方案要根据业务定义 condition 或 request 级事务、状态记录、补偿和最终展示。

### 42. BPM approved 后为什么还可能失败？

真正 DB 写入在最终回调的异步任务中。审批只授予权限，SQL、网络、进程退出和数据冲突仍可能失败；必须看 callback exec、affectedRows 和最终 query。

### 43. 重复 callback 怎么办？

当前没有持久化幂等证据。目标设计用“审批实例引用 + 节点阶段 + 建议版本”形成唯一键，配合持久化状态、Inbox/Outbox、重复回调幂等 ACK 和可重放执行。

### 44. Agent 为什么使用独立审批流程？

来源、审批人、上下文和风险边界不同。显式隔离可以单独禁用、灰度和统计，也避免依赖某个普通业务字段做隐式路由。

### 45. 上游已有结构化请求，为什么不再调用 LLM 优化？

固定结构已是系统间契约。二次 LLM 只会增加字段漂移、漏项、延迟和版本差异；正确做法是直接转换、确定性校验、审批和审计。

### 46. 人工与 Agent 两条链路校验一样吗？

不能默认一样。自然语言路径通常需要实体消歧和知识范围校验，可信上游的结构化路径可能只做 Schema 与领域约束；但两者在进入高风险执行前都应达到统一的作用域、权限和完整性标准。当前实现是否完全一致需要如实说明。

### 47. SQL 超长怎么修？

当前只完成根因定位。不能直接答“每 500 行切批”。要先定原子性和幂等，再考虑按 condition 分组、批内行数/字节双限制、事务/状态表、失败重试和最终回查。

### 48. 这些接口真的安全吗？

代码内没有充分证明所有执行/Admin/Agent 入口都强制鉴权；需要确认网关、内网 ACL、签名、IP 白名单和回调验签。面试中主动区分应用代码与平台边界。

## 四、城市异动诊断 Agent

> 除第 49 题说明当前事实外，本节架构、状态、工具、评测和灰度答案均是下一阶段设计。面试时应使用“我的设计是/实现时会”，不能说成现有系统已经具备这些能力。

### 49. 这个项目现在到底做到哪？

当前证据支持阈值执行底座和完整架构方案，不支持 Hive MCP、多步诊断和效果反馈已正式上线。如果有其他仓库，需补代码和部署材料后才能升级表述。

### 50. 为什么不能直接让 LLM 看指标给原因？

同比、MAD、样本量和口径版本都可确定计算；让 LLM 凭感觉判断不可复现。规则/统计产生事实，LLM 只组织有限假设和决定下一步取什么证据。

### 51. MCP、Function Calling 和 Workflow 有什么区别？

- Function Calling：模型表达要调用哪个工具及参数；
- MCP：标准化工具发现、Schema、连接，并提供客户端访问 MCP Resource Server 的传输层授权框架；它不替代城市、租户、指标、行列和动作等业务对象级授权，ToolAnnotations 也只是提示；
- Workflow：管理长期状态、节点、分支、预算、重试、暂停恢复；
- 规则引擎：执行硬约束和数值计算。

### 52. 如何防止 Agent 编造证据？

方案中事实只能来自工具或确定性程序，并保存为不可变 Evidence；模型只能提出 Evidence 与 Hypothesis 的支持、反驳或不足关系。每个结论引用 `evidence_id`，保留 Tool Trace、数据时间和查询引用；证据分不足时转人工补证或 ABSTAIN，生成报告时程序校验所有引用和数值是否存在。

### 53. 为什么需要数据质量闸门？

分区未产出或口径刚升级时，最聪明的推理也只会生成错误解释。先检查新鲜度、覆盖、重复、版本和特殊事件，不合格就停止。

### 54. 置信度如何计算？

不用 LLM 自报 87%。方案会由程序根据数据质量、证据覆盖与独立性、反证、基线稳定性和工具状态计算 `evidence_score`；有验证集后再做概率校准，并按 risk-coverage 与动作风险设置补证、人工复核或 ABSTAIN 路由。没有校准集时只能使用保守的离散证据状态，不能把它冒充概率。

### 55. 推荐值由谁产生？

LLM 只提出动作方向和理由；确定性推荐器结合已验证证据、当前配置、允许范围、变化速率、冷却期和保护指标，独立判断是否有资格调整，并计算最终方向、候选值或区间。模型不生成约束或数字，也不能直接触发动作；最终建议还要绑定 Evidence、风险、预计影响和回滚条件。

### 56. Workflow 如何暂停和恢复？

我的设计是持久化 `DiagnosisState`：提交 BPM 前保存案件、候选动作版本、建议版本和配置版本；可信回调先进入 Inbox，再恢复同一 Workflow 实例。恢复后重新检查取消、权限、幂等与配置版本。人工产品审核、下游 BPM 状态和执行终态分别建模；BPM 通过只代表获得执行授权，必须由确定性 Action Adapter 执行并回查到 `APPLIED`，才能进入效果观察。

### 57. 如何评估诊断 Agent？

评测设计会拆成 Scope、工具选择、证据覆盖、异常 Top-K、建议合法率、ABSTAIN、重复执行、延迟和效果观察，不能只用最终报告文本相似度；这些指标目前仍是评测方案，不是已有结果。

### 58. 如何灰度？

灰度方案按 Replay → Shadow → Pilot → Canary → Scale：先离线回放；再线上只读且不展示；随后只向人展示事实、Runbook 和 Dry Run；通过门槛后才允许人工确认下的小范围、低风险 BPM；最后用同期对照决定是否扩量。实现时会全程保留开关、范围授权、限流、熔断、回滚和硬停止条件。

### 59. Agent 挂了怎么办？

降级设计是：数据过期则 ABSTAIN；单工具只做有限重试；LLM 不可用时只返回确定性事实；BPM 不可用时保存 Dry Run；数据库状态未知时由 Action Adapter 先查幂等记录和最终配置，不盲目重写。

### 60. 为什么选 LangGraph，而不是写一个 ReAct 循环？

方案选择 LangGraph，是因为这个任务有固定的安全顺序：先权限和数据质量，再异常确认、取证、建议、人工产品审核、下游审批、执行终态和效果观察。实现时会用图显式表达分支、循环上限、Checkpoint 和 Interrupt；LLM 只进入“计划、假设、解释”这些难规则化节点。自由循环最多放在受限的反证子图中，且永远不能获得写工具或无限预算。

### 61. 外部请求为什么不能直接反序列化成 Graph State？

设计中的完整 State 会包含动作权限、建议版本、审核决定和执行引用。若客户端可写这些字段，就可能伪造内部状态，因此计划分成窄化的外部请求、服务端构造的案件输入、内部 Workflow State 和脱敏公开输出；登录主体、授权服务、数据库和 Action Adapter 通过可信运行时 Context 注入，不信任 State 中的身份副本。

### 62. 使用 Pydantic State 是否就保证每个节点输出都合法？

不能。当前 LangGraph 的 Pydantic State 主要验证图入口，不会自动替每个后续节点和最终输出做运行时校验。因此实现方案要求每个模型输出、工具结果、人工编辑和公开输出都通过独立 Schema 显式校验，验证后才能写入 State；这仍是待实现约束。

### 63. 并行取证如何避免互相覆盖？

方案中每个证据节点只返回不可变 Evidence 引用。并行写入字段会使用确定性 Reducer，按 `evidence_id` 去重并校验内容哈希；同 ID 内容冲突时失败关闭。不能用普通列表覆盖或无条件追加，否则同一执行步可能冲突，补证重放也会产生重复证据。

### 64. 快路径命中历史案例后，能否直接生成建议？

设计上不能。历史案例只是候选模式，仍需拉取当前关键证据，检查数据水位、模式版本、必要条件和关键反证，再进入统一证据校验。任何快路径都不能绕开权限、数据质量、Policy、模拟和审批。

### 65. 数据质量降级时允许做什么？

方案中动作集合由“调用者权限 ∩ 数据质量允许动作 ∩ Policy 允许动作”确定。关键数据不可用时只输出数据异常、继续观察或转人工；数据为 `DEGRADED` 时可以给带限制的解释，但首版会硬阻断阈值变更。这个边界必须由程序判断，不能只写在 Prompt 中。

### 66. 一次“人工批准”为什么还不能记成执行成功？

状态设计至少会把人工产品审核、下游 BPM 审批和执行终态建成三组独立字段：产品审核通过不等于已提交 BPM，BPM 提交成功不等于审批通过，BPM 审批通过也不等于配置已生效。只有 Action Adapter 回查配置或权威执行状态并确认 `APPLIED`，才进入效果监控。

### 67. 人工在审批页编辑建议后如何处理？

设计上，编辑结果不能覆盖原建议后直接执行。系统会校验编辑 Schema，创建不可变的新建议版本和新候选动作，使旧审核失效，再重新跑 Policy、当前配置校验、模拟、Diff 和审核，以证明执行的正是人看到并批准的版本。

### 68. 回滚怎样避免误执行成原动作？

方案把回滚建模为独立候选动作，而不是再次执行原建议。它会绑定被回滚的执行引用、反向 Diff、当前配置版本、回滚审核目的和唯一候选标识，经过独立校验与审批；确定性 Action Adapter 只处理审批明确绑定的候选。

### 69. 如何真正做到执行幂等？

实现方案不会使用“先查、没有再提交”的非原子逻辑，而会由服务端生成幂等键，以载荷哈希做数据库唯一原子预占，再通过 Outbox 可靠提交；下游也持久化同一幂等键。同键不同载荷必须拒绝，已有记录按待处理、已应用、失败、未知分支处理，不能把“查到记录”当成成功。

### 70. 人工审批和 T+2h 观察怎样跨进程恢复？

LangGraph 的 `interrupt()` 可以借助 Checkpointer 暂停并在收到恢复命令后继续，但不会自己定时唤醒。方案会把审批事件写入持久 Inbox，以同一 Workflow 标识恢复；外部超时任务用 CAS 处理“批准与过期”的竞争，效果观察由持久化调度器到期投递事件，再恢复监控子流程，而不是假设一个 `WAIT` 节点会自动醒来。

### 71. Checkpoint Store 和业务 Case 表谁是事实源？

我的设计是让 Checkpoint 成为 Workflow 运行状态的权威来源，Case 表只作为面向检索和产品页面的派生投影，并通过可靠事件同步；审批和调度事件通过持久 Inbox 幂等消费。这样避免两个存储分别主写，在进程中途失败时产生页面状态与图状态分叉。该存储关系仍需通过实现和恢复测试验证。

### 72. 如何避免历史回放的数据穿越？

回放设计要求每条证据同时满足 `event_time <= decision_cutoff` 且规范化的 `available_at/ingested_at <= decision_cutoff`。前者限制事实发生时间，后者限制记录当时是否已能被系统读取；allowed lateness 只用于数据质量和水位判断，绝不能放宽纳入条件。模型、规则、配置和知识也保存当时版本。

### 73. 置信度为什么不能直接采用 LLM 自报概率？

未经校准的“87%”没有稳定含义。首版计划先使用程序计算的离散证据状态；有验证集后，再根据证据覆盖、关键反证、DQ、基线稳定性和工具状态形成原始证据分并校准。路由阈值按严重度和动作风险分别确定；模型自报 confidence 最多作为实验特征，不能单独放行高风险动作。

### 74. 什么时候才值得微调？

首版不微调，因为主要瓶颈更可能是数据契约、工具、时序、Workflow 和评测。只有积累经过仲裁、切片覆盖充分的数据，并观察到 Prompt/工具/规则解决不了的稳定模型错误簇，才比较 SFT、小模型蒸馏或分类器。样本量只是项目预算假设，是否继续取决于学习曲线、置信区间、错误饱和和质量/成本收益。

### 75. 为什么不一开始就做多 Agent？

供需、运维、配置等取证可以先由代码并行，单协调器负责冲突和最终结果。只有单 Agent 因上下文规模或独立分支明显退化，且离线评测证明并行子 Agent 的质量收益覆盖额外成本和延迟，才拆只读子 Agent；任何子 Agent 都不能共享写权限。

### 76. QPS 和延迟怎样优化、怎样证明？

先测告警风暴下的完整工作流完成吞吐、队列年龄、工具 QPS、模型并发、P50/P95/P99 和超时率，而不是只测 API 入队。优化顺序是预聚合、独立查询并行、参数指纹缓存、上下文裁剪、大小模型路由和背压降级。具体吞吐和延迟目标只以评测文档为准；取得同数据、同质量门槛的 A/B 压测结果后才可写成实绩。

### 77. 业务收益如何证明不是自然回落？

保存告警时点快照和所有同期人工动作；优先用随机或阶梯灰度，条件不允许时用 switchback、匹配对照或差分中的差分。比较异常持续时间/面积、人工分钟、漏报、告警负担和 Guardrail，并报告样本、效应量、置信区间与干扰。简单“调整前后下降”不能归因给 Agent。

### 78. 这个规划目前能量化讲什么？

能讲的是待测 Baseline、明确的 go/no-go 门槛、压测方案和预期目标，不能讲成线上成果。面试可说“我完成了面向生产约束的演进方案，并把安全、数据、评测和实施拆到可执行任务”；等 Replay/Shadow/Pilot/Canary 真实完成后，再补覆盖范围、样本、准确率、延迟、人工节省和业务效果。

## 五、反问面试官

可根据岗位选择：

1. 团队的 Agent 主要停留在问答，还是已经进入可执行工作流？
2. 高风险工具调用由模型、规则、权限系统和人工分别承担什么责任？
3. 是否有统一的离线金标、线上回放和 prompt/model 版本管理？
4. Workflow 是否需要跨小时/跨天暂停恢复，如何做持久化和幂等？
5. 对 Applied ML，团队如何区分离线模型增益、策略增益和最终业务因果效果？
6. 模型、特征、服务和业务指标分别由哪些团队负责，算法工程师能覆盖到哪一层？
7. 当前最重要的失败类型是模型质量、数据质量、工具稳定性还是执行可靠性？

这些问题既能了解岗位，也能自然展示自己的判断框架。
