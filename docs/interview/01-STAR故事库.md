# 滴滴项目 STAR 故事库

更新日期：2026-09-04

使用方法：不要机械背全文。每个故事记住“冲突—判断—关键动作—结果—反思”五个锚点，按面试岗位选择 2–3 个主故事。

## 故事一：识别 Label 口径迁移造成的虚假突破

适用：算法、数据、技术判断、失败复盘。

### Situation

一次新标签口径试验结果异常漂亮，MAE 从旧模型约 132 分钟降到 75.60 分钟。如果只看总指标，很容易直接汇报“误差近乎减半”。

### Task

证明提升究竟来自特征/模型，还是样本、Label 或时间窗口变化。

### Action

1. 比较旧口径与新口径的 Label 分布和六个时长桶占比；
2. 发现 6–12 小时占比从 19.16% 下降到 5.61%；
3. 计算各桶对总 MAE 的贡献；
4. 在两个口径之间做交叉分布重加权；
5. 追查不同表中相同事件类型编码的业务语义；
6. 重新确定事件集合、删除错误 run 并全量重训；
7. 构建同一工单 ID 的公平对照集。

### Result

证明大幅改善主要来自长尾样本占比变化，而不是模型能力；避免错误模型和结论进入上线决策。正确口径下，最终候选在 318,499 条同工单上的真实 MAE 改善是 2.30%。

### Reflection

应该在全量训练前就冻结“类型数字—业务事件—时间字段—样本分布”合同，并用一天/一周数据做语义验收。

### 一句话

> 我最有价值的动作不是做出一个更好的分数，而是主动推翻了一个非常好看但错误的分数。

## 故事二：用未来 OOT 否定随机 test 的局部最优

适用：模型泛化、实验设计、如何处理领导目标。

### Situation

围绕短时 P25 的一组权重方案，在随机分层 test 上通过率从 41.84% 提高到 68.06%，进一步方案甚至达到 83.43%。

### Task

判断它是否真的值得替换线上模型，而不是只对随机切分或局部指标过拟合。

### Action

- 建立未来 24 天日期 OOT；
- 同时观察全量 MAE、六桶、bias、城市达标和短时指标；
- 将已参与调参的 OOT 标记为非独立验收集；
- 比较短桶收益和 3 小时以上退化。

### Result

发现表面最优方案没有形成稳定替换价值，强短桶权重会明显伤害长尾；最终保留多目标护栏而非追单一 P25。

### Reflection

随机 test 用于快速筛方向，日期 OOT 才回答未来泛化；参与过调参的数据不能继续充当最终独立验收。

## 故事三：定位线上线下预测差异

适用：算法工程、生产排障、跨栈能力。

### Situation

同一个业务 case 的线上与本地预测相差约 9.11 分钟，需要判断是模型、特征处理还是数据快照造成。

### Task

在模型文件、特征顺序、在线预处理、输入向量、数据快照和运行时中定位差异。

### Action

按层排查：

1. 校验模型文件和运行环境；
2. 校验特征数量、顺序和预处理；
3. 固定线上同一次调用的完整输入向量；
4. 比较在线与本地的同向量输出；
5. 核对在线特征快照时间。

### Result

拿到同一次 87 维向量后，线上/本地差异缩小到 0.39945 分钟，约 0.249%；原 9.11 分钟来自混用了不同时点的小时快照，而非模型或顺序错误。

### Reflection

线上线下一致性比较必须固定模型、向量、预处理版本和数据快照；只说“同一个工单”仍然不够。

## 故事四：为 0.25 分钟收益放弃 custom loss

适用：技术选型、权衡、稳定性。

### Situation

custom asymmetric 在标准 test 上比 linear 好约 0.25 分钟，但线上只能使用 XGBoost 0.90 Java runtime，GPU 候选还存在物理树数与 best iteration 不一致风险。

### Task

选择既有离线收益、又能稳定加载和回放的最终模型。

### Action

- 对比总体、分桶和同工单收益；
- 评估自定义目标的兼容与解释成本；
- 固定日期、特征、seed 和树参数，只把建树方式换为 CPU `hist`；
- 固定训练 536 棵物理树；
- 校验文件哈希、XGBoost 0.90 加载和真实样本推理。

### Result

CPU 版相对 GPU 版 MAE 仅增加 0.0959 分钟，得到可稳定部署和校验的产物；最终选择 linear，而不是为 0.25 分钟收益引入额外风险。

### Reflection

模型选择不是离线排行榜，应该比较增益、运行时兼容、观测、回滚和团队维护总成本。

## 故事五：重构三层阈值领域模型

适用：Java、领域建模、系统设计。

### Situation

早期阈值原型把基础值和人工调整混在一起，难以同时表达长期策略、周期性调整和指定日期特例；查询、相对修改和回退语义容易冲突。

### Task

建立一个既能表达复杂维度，又能安全查询和更新的领域模型。

### Action

- 用“城市 → 区域 → 时段 → 周期/指定日期 → 车型 → 配置”的分层领域结构承载内存操作；
- 将数据语义拆为长期基础配置、周期性调整和指定日期特例，不保留内部表或配置类型名称；
- 固化覆盖顺序和默认车型回退；
- 将相对调整换算为对基础值的增量，并让固定阈值保持更高优先级；
- 落库前按周期配置与日期特例的职责分流；
- 更新后重新查询最终合并结果。

### Result

统一支持普通阈值、日期特例、固定阈值、订单工单比和复制操作，并为自然语言、后台接口和 Agent 入口提供同一执行语义。

### Reflection

高风险配置系统的核心不是接口数量，而是覆盖优先级、读改写和失败语义是否能被所有入口共享。

## 故事六：修复单车型更新覆盖其他车型

适用：数据安全、代码审查、线上风险。

### Situation

数据库一行 JSON 同时保存多个车型。只构造目标车型 DTO 再 upsert，会用局部 JSON 覆盖整列，未请求车型和未知扩展字段都可能丢失。

### Task

实现局部语义更新，同时保护整行数据。

### Action

1. 查询当前完整 config；
2. 解析为领域结构；
3. 只修改目标车型；
4. 合并保留其他车型和未知字段；
5. 完整回写；
6. 进一步兼容基础配置已不存在、但调整层仍保留历史增量的车型。

### Result

避免单车型修改破坏同一行其他配置，形成所有 JSON upsert 都要遵循的读改写原则。

### Reflection

MySQL `ON DUPLICATE KEY UPDATE config = VALUES(config)` 是整列替换；API 看起来局部，不代表数据库操作天然局部。

## 故事七：发现合法 JSON 中的批量静默漏项

适用：LLM 评测、Agent 安全、结构化输出。

### Situation

候选模型可以返回严格合法 JSON，但真实回放中出现 9 城请求只返回 1 城、5 项请求漏一项的情况。格式指标无法发现。

### Task

定义比“JSON 可解析”更接近业务执行的正确率，并在代码中阻断部分执行。

### Action

- 将输入拆成可独立核对的原子指令；
- 为每个原子指令携带可回溯标识；
- 由程序检查输入目标与输出目标是否完整一一对应；
- 区分 JSON、字段一致、功能等价、语义可接受和安全阻断；
- 建立 42 条金标、239 次调用和 43 条真实日志回放；
- 对失败样本验证重试，但不把小样本恢复率当长期 SLA。

### Result

离线候选原始 40/42，经 Java 校验后 41/42，0 截断；同时明确暴露了批量漏项仍需重试/阻断治理，而不是宣称 100%。

### Reflection

结构化输出只解决“形状”，完整性和业务语义必须由程序和任务级评测承担。

## 故事八：把人工和 Agent 的信任边界分开

适用：Agent 架构、API 设计、权限边界。

### Situation

外部 Agent 需要调用已有阈值执行能力。最简单的方式是复用人工入口，再用普通调用方字段隐式判断来源，但审批人、回调和风险范围并不相同。

### Task

在复用底层执行能力的同时，让人工和 Agent 可以独立控制、审计和回退。

### Action

- 新建独立的外部 Agent 结构化入口；
- 增加请求追踪标识和外部回调；
- 使用独立的 Agent 审批流程；
- 将可执行动作收窄为普通整数阈值；
- 上游已有固定结构化请求时直接校验转换，不再调用第二次 LLM；
- 中间审批只记录和确认，最终审批才触发执行。

### Result

形成了人工入口与外部 Agent 入口可独立配置、审批和审计的边界，同时复用既有查询、BPM、执行与审计服务；固定结构化请求不再经过第二次 LLM，避免了这一步可能引入的字段漂移和额外延迟。是否已经形成独立启停、使用量统计和长期效果，仍需另行补证。

### Reflection

当前仍缺持久化幂等、Agent 实体归属校验和 DB 完成结果回传；入口隔离只是安全闭环的一部分。

## 故事九：定位 1,000+ 行批量 SQL 超长

适用：故障排查、数据库、诚实复盘。

### Situation

用户预查询正常、BPM 也成功，但最终配置没有生效，日志表明写入阶段触发了 SQL 长度限制。

### Task

确定失败发生在哪个阶段以及 SQL 为什么突然变大，同时不影响查询和审批流程。

### Action

- 按 parse → pre-query → BPM submit → callback → DB write 分段查日志；
- 定位真正写库发生在最终审批后的异步执行阶段；
- 追踪 time range × weekday × vehicle 展开；
- 定位配置展开与无界批量 upsert 产生超长单条 SQL；
- 对大小不同的成功/失败样本比较展开规模；
- 撤回未明确事务语义的临时串行方案。

### Result

确认大批量条件展开后的单条 upsert 超过数据库链路限制，而较小对照样本成功；根因定位完成，但可靠分批、事务和幂等治理尚未被证明已经上线。

### Reflection

面试中必须说“定位并设计治理”，不能说“已修复”。真正方案要先回答事务、部分成功、BPM 重试和幂等。

## 故事十：设计证据驱动的城市诊断 Agent

适用：系统设计、Agent、技术规划。注意这是方案设计，不是已上线 STAR 业绩。

### Situation

已有阈值平台只解决“知道要改什么”后的执行；运营真实问题通常从“为什么指标异常、要不要改”开始。

### Task

设计一个能使用经营数据、形成可审计诊断、但不会让 LLM 越权写生产的 Agent。

### Action

- 规划用受控的只读领域 API/MCP 暴露固定 Schema 工具；
- 设计先经过数据质量闸门和确定性异常检测；
- 将 LLM 限制为生成有限假设、选择下钻工具并建立可审核的证据关系；
- 设计由程序计算并校准证据分，再映射为补证、人工复核或 ABSTAIN 路由，不采用 LLM 自报置信度；
- 让 LLM 只给动作方向和理由，由确定性推荐器计算资格、候选范围与数值，执行前再做 Dry Run 和配置版本检查；
- 设计将人工产品审核、下游 BPM 和执行终态分开保存，Workflow 收到可信事件后再恢复；
- 分 Replay、Shadow、Pilot、Canary 和 Scale 逐级验证；动作协议、终态回查能力与效果评估方案在 Canary 前补齐，真实执行可靠性和业务效果则在 Canary/Scale 中验证。

### Result

形成与现有阈值执行底座兼容的完整架构和演进路线，明确 MCP、Function Calling、Workflow、规则和人审的边界。

### Reflection

当前还没有足够证据说明诊断循环已生产落地；这个故事应展示设计判断，不应包装成线上收益。

## 行为面收尾模板

每个故事最后用一句反思收尾：

> 这件事让我后来形成了一个固定做法：______。如果重做，我会在项目开始时先把 ______ 纳入验收，而不是等出现问题后再补。

这样比“问题最终被我完美解决”更可信，也更能体现成长。
