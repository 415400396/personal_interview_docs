# 项目管理与汇报模板

用途：把需求对齐、主动汇报、风险暴露和效果回收变成固定动作。按项目规模裁剪，不需要为小任务制造文档负担。

## 1. 接需求后的复述

```text
我先确认一下理解：

背景/用户：
当前问题：
希望取得的结果：
交付物：
完成标准和指标：
本次范围：
明确不做：
预计里程碑和 ETA：
当前依赖/风险：

我的计划是先做 A，再做 B，最后通过 C 验证。
如果以上理解一致，我会按这个范围推进。
```

最低要问清：Why、User、Goal、Scope、Metric、Deliverable、ETA、Dependency/Risk。

## 3. 周状态 / 阶段同步

```text
【结论】项目当前正常 / 有风险 / 已阻塞；总体完成约 __%。

【本周完成】
- （填写）

【当前结果】
- 指标/证据：
- 与 Baseline/目标的差距：

【风险与需要的帮助】
- 风险及影响：
- 已尝试：
- 需要谁在何时做什么：
- 备用方案：

【下一步】
- （填写）

【ETA】
- 下一里程碑：
- 总体完成时间是否变化：
```

汇报重点不是罗列工作量，而是让对方知道：当前结论、是否需要决策、风险是否影响承诺、下一步何时发生。

## 4. Blocker 升级

```text
【结论】__ 依赖当前阻塞 __，若在 __ 前未解除，将影响 __。

【影响】质量 / 范围 / 安全 / 里程碑 / 最终 ETA：
【已确认事实】
【已尝试动作】
【需要的支持】希望 __ 在 __ 前确认/提供 __。
【备用方案】
【下次检查/升级时间】
```

不要只发送“麻烦帮忙看看”。每次同步必须包含明确请求和下一检查点。

## 5. Bug / 线上问题汇报

```text
【结论】问题已定位 / 尚在定位，当前影响 __，预计 __ 更新下一次进展。

【原因】已确认 / 当前假设：
【影响范围】用户、城市、数据、功能、时间：
【是否影响核心链路】
【临时止损】
【永久修复】
【ETA】
【验证方式】
【防复发】测试 / 校验 / 监控 / 流程：
```

排查过程放在结论和影响之后。尚未确认的原因必须标明“假设”。

## 6. 决策记录

```text
日期：
问题：
已知事实：
选项 A / B / C：
选择：
原因：
代价和风险：
谁已确认：
何时重新评估：
```

只记录会影响范围、指标、架构、兼容性或 ETA 的关键决策。

## 7. Demo 前检查

- 用一句话说明听众、目的和希望获得的决策；
- 前 30 秒先说结论与价值；
- 页面顺序固定，关闭无关窗口和通知；
- 准备稳定测试数据，不现场查找文件；
- 明确正常路径、一个关键失败路径和当前限制；
- 提前跑一遍并计时；
- 准备截图/录屏作为网络或环境失败的备用材料；
- 结尾明确下一步、Owner 和 ETA；
- Demo 后发送结论和行动项，不让决策只存在于会议里。

## 8. 上线与效果回看

上线前必须填写：

- 灰度范围：
- 监控指标：
- Guardrail：
- 回滚条件和负责人：
- 效果数据来源和 Owner：
- 第一次效果回看日期：
- 最终复盘日期：

效果同步：

```text
【结论】达到 / 部分达到 / 未达到目标。
【样本与时间】
【Baseline 与结果】
【业务、系统和护栏指标】
【能否归因及限制】
【异常/反例】
【决策】放量 / 保持 / 继续观察 / 回滚 / 停止。
【下一步、Owner、日期】
```

## 9. 项目收尾复盘

```text
Problem：为什么做。
Goal：原目标与成功标准。
Decision：最关键的三个决策及取舍。
Delivery：真正交付到哪一层。
Impact：模型、系统、采用和业务结果。
Failure：没有达到什么，为什么。
Collaboration：依赖怎样推进，有何不足。
Lessons：下次复用或避免什么。
Next：未完成事项、Owner 和日期。
Evidence：报告、指标、代码、日志或公开链接。
```

项目没有提升也可以正常收尾，但必须给出可信的无收益结论和停止/调整建议。
